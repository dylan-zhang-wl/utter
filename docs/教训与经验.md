## 一、流程上的教训（代价最大的一类）

### 1. 遇到不平凡的技术问题，先查同类开源，再动手

2026-08-10 一整天，分别撞上四个问题：剪贴板还原竞态、无输入框时粘贴静默丢失、
中英混说被翻译、繁简输出不稳定。**四个全部在同类开源项目或上游 discussion 里
写过。** 技术判断最后都对，但流程错了，代价是作者陪测一整天。

判据：**如果一个问题让你想说「我来想想怎么解决」，那就是该先查的时刻。**

已确认可参考的：

| 项目 | 已验证的做法 |
|---|---|
| [VoiceInk](https://github.com/Beingpax/VoiceInk) | 粘贴前查 `AXRole` 确认有输入框；剪贴板还原延迟可配置；type-out 作兜底 |
| openai/whisper [#976](https://github.com/openai/whisper/discussions/976) | code-switching 是设计限制：每 30s 窗口只认一个语言 |
| openai/whisper [#277](https://github.com/openai/whisper/discussions/277) | 繁简输出不稳定，已知问题 |
| [sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/) | 二十个 offline 加载器，全 onnxruntime、不碰 torch |

### 2. 但查开源不替代自己测量

VoiceInk [#687](https://github.com/Beingpax/VoiceInk/issues/687) 那个「间歇性空转录」
至今开着，维护者复现不了。**同一个 bug 我们量出来了**——首次开麦 713ms，句子开头
被吃掉。差别不在聪明，在于我们建了埋点。

### 3. 不要在没有测量的情况下"修"一个假设出来的原因

长句在停顿处切分那次：理论完全说得通（Whisper 看得见句子形状才会打标点），
上线后一测——

```
16.4s 不切 → 4 个标点
24.2s 切开 → 2 个标点
```

**更差，而且慢了五倍。** 已回滚。这条同时违反了第一天就写下的铁律 2
（Whisper 内部把 mel 补到 30 秒，2 秒块和 15 秒块几乎同价）。

### 4. 仪表本身会撒谎，先校准仪表

`last_timing` 的赋值写在 `on_text()` 之后，而报告正是 `on_text` 打印的——
终端上每一块耗时**属于上一句**。一整轮分析是拿「37.8 秒音频」配「11 个字的
转写」做的，两者根本不是同一句。

**排查陷入僵局时，先怀疑自己的测量工具。**

### 5. 会假通过的验证命令，比没有验证更糟

`~/.venvs/utter/bin/pip list | grep torch` 永远打印空——uv venv 不装 pip，
管道 grep 的是空输出。这条命令"验证"了铁律 5 好几次，其实什么都没验证。
正确的是 `uv pip list --python ~/.venvs/utter/bin/python`。

## 二、Whisper / ASR 的坑

### 6. 静音会让 Whisper 凭空编句子

两秒空房间的底噪，Whisper 交出 `"you"` 和 `"Good job."`。**转录前必须过
`vad.has_speech`。** 把编造的句子注入作者的文档，比任何延迟问题都严重。

### 7. temperature 阶梯要有界，但不能取消

原铁律写的是「必须 `temperature=0.0`」（标量）。那样确实把最坏情况从 8–11 秒
压到 1 秒，但漏了一件事：**那条阶梯的用途正是逃出复读循环**。标量意味着无处
可退，模型一旦开始复读就复读到窗口结束（实测收到过同一短语重复五十遍）。

现值 `(0.0, 0.2)`——两级封顶，最坏约 2.2 秒，正常情况零额外代价。
外加一层确定性的 `collapse_repetition` 兜底，且必须**大声报告**折叠了多少处。

### 8. 不指定语言，每句多花约 0.9 秒

多一遍语言检测 encoder。但对中英混说的人，这 0.9 秒是必要开销——
指定 `zh` 会把英文**翻译**成中文，而不是转写。

### 9. Whisper 的中文标点在任何长度上都稀疏

不是 bug，是训练数据的性质（中文语料多为字幕，字幕不带标点）。
配置改不动，只能靠 LLM 润色补，或换模型。

### 10. `initial_prompt` 上限 223 token，超出**从头静默截断**

`n_text_ctx // 2 - 1`。实测作者的 30 条术语表 = 340 字 = 133 token。
超出后最早的词会消失且毫无提示——一个安静失效的术语表。现已在启动时检查。

## 三、模型选型（2026-08-10 实测）

| 引擎 | 英文术语 | 中英混说 | 纯中文 | 速度/每秒音频 | 常驻内存 |
|---|---|---|---|---|---|
| **Whisper turbo 自动** | **全对** | 英文在 | 好 | 90–146ms | 474 MB |
| SenseVoice int8 | 差 | **吞掉英文** | 好，标点更全 | **14–20ms** | 549 MB |
| FireRedASR2-CTC | 中（全大写） | 乱码 | **无标点** | 151–174ms | — |

### 11. SenseVoice 在中文句子里不是听错英文，是删掉英文

> 原话：我这一节想写的是 literature review，大概在 2.1 的位置
> 输出：我这一节想写的是 **re盖** 在2.1的位置

`literature matrix` 整个消失。**中文读着通顺，术语没了**——静默丢失，
事后不会发现。对英文几乎全是术语的使用者，这一条单独否掉它作默认档。

### 12. 文件小 ≠ 占内存小

SenseVoice 权重 228MB 却占 549MB 常驻；Whisper 1.6GB 只占 474MB。
onnxruntime 预分配内存池，MLX 走 Metal 统一内存按需加载。

### 13. 量化不是英文差的原因

同一仓库的 fp32（938MB）与 int8（239MB）返回**逐字相同的错**，且慢一倍。
是模型本身只有 234M 参数。

### 14. SenseVoice-Large 没有开放权重

只在阿里云 API 上。本地不存在"换个大档"这条路。

### 15. provider 抽象是这个项目回报最高的一次投入

换 Whisper → SenseVoice，provider 文件之上**一行没改**。sherpa-onnx 1.13
已内建 Qwen3-ASR / FireRedASR / Fun-ASR-Nano 等二十个加载器，将来出现更好的
模型，接进来只是加一个小文件。

## 四、macOS 集成的坑

### 16. 两个 pynput Listener + 一个 Controller = SIGABRT，无 traceback

pynput 的 macOS 后端从每个 listener 线程进入**不可重入**的 `keycode_context`。
两个 listener 单独没事，加上注入用的 Controller 必崩。**一个进程一个 Listener，
多个 matcher。**

### 17. `Key.alt` 和 `Key.alt_l` 是同一个枚举成员

darwin 后端里两者 vk 相同，Python 的 Enum 把后者变成前者的别名。
右 Option 是 `Key.alt_r`，独立。所以 `<alt_l>` 能工作，但它同时匹配"泛左 alt"。

### 18. `activateWithOptions_` 是异步的

日志说注入到 A，文字落在 B。必须**轮询等到前台真的换过来**再粘贴。

### 19. 剪贴板要在粘贴真正落地之后才还原

25 个单元测试全过，因为它们检查的是最终状态而不是**顺序**。
作者眼看着之前复制的 shell 命令被贴进文档。

### 20. macOS 有两个都叫「辅助功能」的设置页

一个是功能页（VoiceOver、缩放），一个是隐私里的权限名单，隔一次点击、名字一样。
权限发给**发起进程的那个 app**（终端），不是 Python。改完要 ⌘Q 完全退出再开。

### 21. 蓝牙耳机同时当麦克风，会被拖进通话模式

A2DP → HFP，单声道、低码率、额外延迟。作者看到的现象是"视频音画不同步、
系统音量变了"，完全不像听写工具干的。代码防不住，只能**不主动触发**
（共用设备时跳过音频预热）并**明说**。

### 22. 忘记退出的 daemon 会安静地毁掉一切

一个 10:26 启动的实例活到 21:30——终端标签早关了，进程还在，
20 个线程、PortAudio 和 CoreAudio 都挂着，**照样抢热键和麦克风**。
按一次键唤醒两个进程去抢同一个设备。从外面唯一的症状是"听写变差了"。
现已加 pid 锁。

### 23. 「advertises input channels」不等于「能录到声音」

作者机器上有扬声器、两个虚拟录音设备、一个会议 app 都报告有输入通道，
全都能打开、全都返回纯静默。**`utter mics` 必须真的打开设备录一下**，
光列举 CoreAudio 的回答会把人坑死。

## 五、还没做好 / 已知不足

- **打包**：还是要开着终端跑 `utter dictate`，没有 `.app`（P4）。
- **注入落点**：文字落在**松开热键时**的前台窗口，不是按下时的。作者已表示暂不修。
- **边说边出字**：还没有（P2b）。而且与铁律 9（注入过的文字永不回改）冲突——
  只能按停顿切句、一句定稿一句注入，代价是润色看不到整段上下文。
- ~~**润色**：从未对着真模型验证过提示词~~ —— 2026-08-10 已验证并接线，见第六节。
  **仍待观察**：守卫会不会误伤（比如模型把英文术语的大小写规范化）。
- **术语表不会自己变好**：手写的静态列表，且有 223 token 天花板。
  `utter vocab add` 和从 Obsidian / Zotero 自动收词都还没做。
- **应用兼容表**：需要在真机上逐个 app 试注入，还没做（P2a Task 7）。
- **听模式（会议记录 + 翻译）**：v1 的 Tauri 界面还在，但走的是旧管线，
  sidecar 链路是断的。P2b/P3 的事。
- **存档只增不减**：实测 227 字节/段、1624 段 = 360 KB 文字。
  因为铁律 3 不存音频，所以增长可以忽略；`utter sessions --prune N` 可手动清。
  同类工具（VoiceInk、Superwhisper）存音频，同样用量一年是几十 GB 级。

## 六、润色（2026-08-10 真模型实测）

### 24. Vertex AI 用云凭据，不需要 API key

作者有 Google Cloud 额度、没有 Gemini API key。Vertex 收的是 OAuth bearer token，
所以能直接用 gcloud 的凭据。它也有 OpenAI 兼容端点，于是复用现成的 client：

```
https://aiplatform.googleapis.com/v1/projects/{PROJECT}/locations/global/endpoints/openapi
```

实测**不需要** `x-goog-user-project` 头。模型 ID 要带 `google/` 前缀。

### 25. 一台机器上可能有两个 Google 身份，而 ADC 未必是你以为的那个

作者机器上 ADC 属于 `dylanzhang…`（另一个工具写的，quota 项目是它托管的），
而 gcloud 的活动账号是 `eldspook…`，后者才是 Vertex 项目的 owner。
**同一个请求：ADC 403，gcloud 凭据 200。**

排查方法（不打印 token）：

```bash
curl -s -X POST https://www.googleapis.com/oauth2/v3/tokeninfo \
  --data-urlencode "access_token=$(gcloud auth application-default print-access-token)"
```

不要贸然 `gcloud auth application-default login` —— 那会**覆盖另一个工具正在用的
ADC**。provider 因此两条都试，谁成谁留。

### 26. Flash-Lite 比 Flash 快 7 倍，输出一模一样

| 模型 | 同一句润色 |
|---|---|
| `google/gemini-2.5-flash-lite` | **980 ms** |
| `google/gemini-2.5-flash` | 6946 ms |

文字逐字相同。润色是简单活，上推理档是花钱买一个提示词整篇都在压制的能力。

### 27. ⚠️ 最重要的一条：提示词禁止不了模型改你的话

铁律 10 的提示词**加粗写着**「不得改写措辞、不得增删内容」。真模型实测：

| 档位 | 实际动作 |
|---|---|
| light | 一字未改，只补标点 ✅ |
| **medium** | 删掉了「呃」**和「因为」** ❌ |
| **heavy** | 把「这个我觉得是」改成「我觉得这个是」❌ |

「因为」是因果连接词 —— 删掉它，一个因果论断变成了并列陈述。
「这个我觉得」变「我觉得这个」是词序改写。

**两个输出都读着非常通顺。** 这正是危险所在：作者重读一遍不会发现，
而音频已经没了。

于是加了**机械守卫**（`content_signature` / `content_changed`）：
把标点、空白、口水词剥掉之后，润色前后的字符序列必须**完全相同**，
否则整段降级回原始转录并在日志里说明删了什么、加了什么。

这条守卫连「模型帮你改对了」也拦 —— 比如把误听的「规化」纠正成「归化」。
听起来可惜，但铁律 10 没有「改得对就可以」这个例外：一个不能确信文字属于自己的
作者，只能逐字对着音频重读，而音频已经不在了。

**教训一般化：把规则写进提示词是请求，不是保证。凡是「模型不许做 X」的地方，
都要问一句「如果它还是做了，我能不能机械地发现」。**

### 28. 守卫要「合并」，不要「否决」——否决会把功能整个废掉

第 27 条加的是一个**全有全无**的守卫：内容有变就整段驳回、退回原始转录。
作者一开真机就废了：

```
polish changed the content (删掉了「那个用那个是哪一个的的但是」), keeping the raw transcript
polish changed the content (删掉了「这个和这个」, 加上了「""""那个"」), keeping the raw transcript
polish changed the content (删掉了「是的然后你看去」), keeping the raw transcript
```

**每一句都被驳回，于是开了润色跟没开一样。** 两个原因叠在一起：

1. **忽略集漏了弯引号 `“ ”`。** 模型极爱加引号，于是「加了引号」被判成「加了内容」。
   教训：这种字符白名单要**宁滥勿缺**，漏一个字符的代价是功能失效。
2. **就算提示词只说补标点，模型还是会顺手删。** 它删了口吃的「的的」、
   删了「是的然后」、甚至删了「但是」。**指令改不掉这个倾向。**

改成 `apply_punctuation(raw, polished)`：**按内容字符对齐两个文本，输出走原始转录
的字符和顺序，只把模型放的标点插进字符之间的空隙**（空隙先过滤成纯标点，
所以模型凭空加的字进不来）。

于是铁律 10 从「一条会失败的检查」变成「构造上的性质」——
输出的内容永远就是转录的内容。模型删的字自动回来，模型改的词序自动复原，
模型答非所问就等于没润色。

顺带一条决定：**大小写也从转录取，不从模型取。** 作者的术语表里有
`van Leeuwen`（全名时 v 小写），模型一定会「纠正」成 `Van Leeuwen`。
句号是收益，大写是猜测。

**一般化：当一个安全检查开始否决绝大多数正常输入时，问题多半不在输入，
在于「否决」这个形状本身选错了。能合并就不要否决。**

## 七、对照开源方案：我们缺什么（2026-08-11）

对照 [VoiceInk](https://github.com/Beingpax/VoiceInk)（macOS 上最成熟的开源同类）
与 [faster-whisper-dictation](https://github.com/bhargavchippada/faster-whisper-dictation)
逐项过了一遍。

### 已经有的

| 能力 | Utter | 说明 |
|---|---|---|
| 本地转录 | ✅ | Whisper turbo / SenseVoice，可换 |
| 按住说话 | ✅ | 左 Option |
| 开关模式 | ✅ | 双击左 Control |
| **边说边出字** | ✅ | 2026-08-11，VAD 分句逐句定稿 |
| 光标处注入 | ✅ | 剪贴板粘贴 + 还原 |
| 术语表 | ✅ | 但**手工维护**，见下 |
| LLM 润色 | ✅ | 而且是**机械保证**不改字，比同类都严 |
| 历史存档 | ✅ | 纯文字，`utter sessions` 可读、可清 |
| 菜单栏 + 开机自启 | ✅ | 2026-08-11 |
| 100% 本地可选 | ✅ | 润色可关，关了完全离线 |

### 缺的（按重要性）

1. **按 app 切配置**（VoiceInk 的 "app detection"）。在 Word 里要正式书面语、
   在终端里要不加标点、在微信里要短句 —— 现在只有一套全局设置。
   **这条对作者最有用**，因为他在 Obsidian 写论文和在终端敲命令是两回事。
2. **术语表不会自己长**。VoiceInk 有 "Personal Dictionary" 加文本替换。
   我们是一个手写 JSON 列表，还有 223 token 天花板。
   缺 `utter vocab add`，也缺从 Obsidian / Zotero 自动收词。
3. **没有首次运行向导**。VoiceInk 有 onboarding 引导权限与模型下载；
   我们靠 `utter doctor` 加一个启动时的弹窗。
4. **不能分发**。见下节。
5. **没有自动更新**（VoiceInk 用 Sparkle）。对单人自用不重要。
6. **没有应用兼容表**（P2a Task 7）—— 哪些 app 能粘、哪些不能，还没逐个试过。
7. **录音时不暂停音乐**。VoiceInk 有；小事，但每次都要手动按暂停。

### 有意不做的

- **语音助手模式**（VoiceInk 的 "conversational assistant"）—— 这是另一个产品。
- **屏幕内容感知**（"understands your screen content"）—— 要读屏幕，隐私代价太大。
- **99% 准确率这类宣称** —— 本项目的立场是量出来的数字，不是形容词。

### 我们比它们严的地方

**润色的内容守卫。** 同类工具的 "AI enhancement" 都直接采用模型输出。
我们做不到相信它：实测 gemini 和 gpt 在明令禁止的情况下照样删「因为」、
调词序。所以 `apply_punctuation` 只取模型的标点、字一律来自转录 ——
**铁律 10 是构造上的性质，不是一条会失败的检查。**

对一个口述学术论证的人，这个差别不是洁癖：一个读着通顺但论断被改过的句子，
事后不可能发现，而音频已经不在了。

### 29. PortAudio 只在进程启动时枚举一次设备 —— 常驻进程会一直用旧列表

作者早上戴上 AirPods，按热键，连着两次：

```
utterance 0 contained no speech, discarded
utterance 1 contained no speech, discarded
```

daemon 是凌晨 00:12 起的，那时 AirPods 没连，`[1]` 是 Redmi 音箱。
早上 AirPods 连上，系统默认变了、**索引整体挪了位**（`[1]` 成了 AirPods，
Redmi 退到 `[3]`），但**进程里的 PortAudio 还停在旧列表上**。

于是它照着旧索引开了一个已经不对的设备，**录到纯静音、全程零报错** ——
因为「你问了一个没在听的设备」在 CoreAudio 看来不算失败。

这是本项目第三次撞上同一类问题（前两次：`utter mics` 那个「报告有输入通道 ≠ 收得到声音」、
共用设备被拖进通话模式）。**音频设备这一层，任何"启动时读一次"的假设都是错的。**

修法：每次开麦前 `sd._terminate(); sd._initialize()`，实测 **4ms** ——
相对 CoreAudio 开流本身的 240ms 可以忽略，所以不做「聪明地判断硬件是否变了」，
每次都重新枚举。

**一般化：常驻进程和一次性命令的假设不一样。凡是"启动时读一次"的东西
（设备列表、权限、配置、模型 ID），都要问一句"跑三天之后它还对吗"。**

### 30. 菜单栏 app 必须先把图标放上去，再做慢的事

作者双击 Utter.app，**一分多钟屏幕上什么都没有**，于是说「打不开这个软件了」。
他的判断完全正确 —— 从他能看到的证据出发，只能得出这个结论。

实际发生的：

```
10:29:21  Utter.app starting
10:30:40  model warmed in 77.29s     ← 79 秒的空白
10:30:40  ready
```

`LSUIElement` 的 app **没有 Dock 图标、没有窗口、没有启动反馈**。而我们把三件慢事
全放在了创建菜单栏图标之前：解析语音 provider（要连 Hugging Face）、
等辅助功能授权、预热模型（实测 1.7 秒到 **77 秒**，取决于权重还在不在页缓存里）。

**这三件都不需要主线程。** 改成：拿到锁 → 立刻建 NSApplication 和菜单栏图标
（带一行「启动中…」状态）→ 其余全部丢进后台线程 → 主线程直接进 run loop。
实测**6 秒内图标就在了**，而且菜单里写着它正在干什么。

外加就绪时发一条通知横幅，和一条 `utter status` 命令 ——
「我看不到图标」和「它没在跑」必须能区分开，而不是都表现为「什么都没有」。

**一般化：GUI 程序里，"先干活再画界面" 永远是错的顺序。**
用户对「没反应」的默认解释是「坏了」，而且这个解释通常是对的 ——
只有在你把反馈做出来之后，它才变成错的。

### 31. `exec` 出去的 .app，LaunchServices 不认它启动完成

图标不出现，查了一个小时，最后是两个独立的原因叠在一起。

**原因一（我自己上午引入的）：菜单每次重画都在重启 PortAudio。**

早上修「戴上耳机不切换」时，我把 `refresh_devices()`（`sd._terminate()` +
`sd._initialize()`）放进了 `shared_with_output()`。而菜单栏的告警行每次
`_rebuild()` 都会调它 —— 于是**启动过程中整个 CoreAudio 连接被反复拆了又建，
就在主线程上**，状态项因此从来没被布局过。

`isVisible()` 一直返回 `True`，`frame` 却是 `32×0` 停在原点。
**「可见」和「有位置」是两件事**，而只有后者决定你能不能看见它。

**原因二：启动器用 `execv`。**

`Contents/MacOS/Utter` 是个 C 小程序，`execv` 成 Python。这让进程号不变、
`CFProcessPath` 也保住了 bundle 身份（权限归 Utter 而不是 Python），
看起来很干净 —— 但 **LaunchServices 启动的那个可执行文件已经不存在了，
它永远等不到「应用启动完成」**。

结果是个非常刁钻的现象：
**同一个二进制，从终端跑图标正常，`open` 打开就没有。** 其他一切都正常
（热键、权限、日志、AX 树里能查到菜单项），只有布局不发生。

改成 `posix_spawn` 一个子进程再 `waitpid`：父进程留在原地当
LaunchServices 认识的那个 app，Python 作为子进程跑（子进程的处境和"从终端跑"
一样，而那是可行的），并转发 SIGTERM/SIGINT 保证退出时不留孤儿。

**一般化两条：**
1. **别把「顺手做点新鲜事」塞进每帧都会跑的路径。** 一个 4ms 的设备重枚举，
   放在开麦前是对的，放在菜单重画里就毁了启动。
2. **`.app` 的主可执行文件不要 exec 走。** 包装式启动器必须留在原地。

### 32. 麦克风权限看代码签名，`CFProcessPath` 骗不过它 —— 而被拒时它给你静音，不给你报错

作者按热键，日志说「没听到」。加了诊断之后：

```
设备=AirPods Pro  时长=6.5s  峰值=0.0000  ← 纯静音
```

**恰好为零，持续 6.5 秒。** 安静房间的真麦克风也会有约 0.001 的底噪，
**精确的 0 不是安静，是 macOS 在拒绝。** 而它拒绝的方式是**一直给你静音，
不报任何错** —— 打开流成功、回调正常、每一帧都是 0。

原因：`.app` 的启动器指向 `~/.venvs/utter/bin/python`。
`CFProcessPath` 能让 CoreFoundation 认为进程属于这个 bundle（辅助功能因此归了
Utter），但 **TCC 判的是代码签名**，而那是个在 bundle 外面的 anaconda 二进制。
麦克风申请**一毫秒返回 refused，连弹窗都没有**。

实测矩阵（这两件事互相独立，我一度把它们混在一起）：

| | 菜单栏图标 | 麦克风 |
|---|---|---|
| `exec` 到外部 python | ❌ | ❌ 秒拒 |
| `spawn` 外部 python | ✅ | ❌ 秒拒 |
| **`spawn` bundle 内的 python** | **✅** | **✅ 弹窗并授权** |

解法：**把解释器复制进 `Contents/MacOS/python`，和 bundle 一起签名。**
它是静态链接的（`otool -L` 只有 libSystem），5.6MB，靠 `PYTHONHOME` 找标准库、
`PYTHONPATH` 找 venv 的包。这样发出麦克风申请的那个进程**就是** Utter。

**一般化：包装式 .app 想拿到权限，真正运行的那个二进制必须在 bundle 里、
并且被一起签名。任何"让系统以为我是它"的技巧，在 TCC 面前都不成立。**

顺带记一条排查心法：**精确的 0 值几乎不是物理量，是拒绝。**
真实传感器有噪声；一列完美的零来自软件里的某个 `if`。

### 33. Whisper 会在静音里编出「字幕志愿者」，而且它进了作者的文档

存档里翻到的：

```
转录: 字幕志愿者 李宗盛。
```

**没有人说过这句。** Whisper 的中文训练数据大量来自视频字幕，没东西可转录时它就
去够片尾字。VAD 门槛是第一道防线、也确实挡住了大部分，但它回答的是
「有没有人在说话」，不是「这段输出是不是真的」—— 一声咳嗽就够给模型一个开口。

`is_hallucination()` 只丢**整句都是套话**的输出。第一版写成了「包含套话 + 长度上限」，
那样会丢掉

> 这一节我要讨论字幕志愿者这个群体在数字人文里的位置

这恰恰是作者会说的句子。**丢掉他真说过的话，比放过一句假话严重得多（铁律 8）**，
所以改成「把套话都剥掉，看还剩多少」：幻觉剥完几乎什么都不剩，真句子剥完还是句子。

### 34. `load()` 永不失败 + 有人接着 `save()` = 永久丢数据

作者发现「大语言模型」被听成「大圆模型」。这是**转录**错误，润色按设计不会碰它
（`apply_punctuation` 的字一律来自转录）。修法在上游 —— 加进术语表。
结果一打开发现**术语表只剩 7 条，原来的 30 条没了。**

机制比这一次事故重要。`load()` 被刻意设计成永不失败：**打不开 app 的人，
也没法用 app 去修那个让它打不开的设置**。但「永不失败」意味着它返回默认值，
而任何**接着写回去**的调用者，就把一次临时的读取问题变成了永久丢失 ——
`_save_config` 每次点菜单都在做这件事。

于是加了 `load_or_none()`：文件存在但读不了时返回 None，写入方看到 None 就
**不写**。一个菜单开关的价值低于那个文件。`_load_field_by_field` 也改成
**说出它丢了哪些字段**，不再默默丢弃。

**一般化：「宽容地读」和「照读到的写」是两个策略，凑在一起就是数据丢失。
凡是 read-modify-write，中间那个 read 必须能说「我没读好」。**
