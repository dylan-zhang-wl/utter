## 一、流程上的教训（代价最大的一类）

### 1. 遇到不平凡的技术问题，先查同类开源，再动手

2026-08-10 一整天，分别撞上四个问题：剪贴板还原竞态、无输入框时粘贴静默丢失、
中英混说被翻译、繁简输出不稳定。**四个全部在同类开源项目或上游 discussion 里
写过。** 技术判断最后都对，但流程错了，代价是耗掉了一整天的人工复测。

判据：**如果一个问题让你想说「我来想想怎么解决」，那就是该先查的时刻。**

已确认可参考的：

| 项目 | 已验证的做法 |
|---|---|
| [VoiceInk](https://github.com/Beingpax/VoiceInk) | 粘贴前查 `AXRole` 确认有输入框；剪贴板还原延迟可配置；type-out 作兜底 |
| openai/whisper [#976](https://github.com/openai/whisper/discussions/976) | code-switching 是设计限制：每 30s 窗口只认一个语言 |
| openai/whisper [#277](https://github.com/openai/whisper/discussions/277) | 繁简输出不稳定，已知问题 |
| [sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/) | 二十个 offline 加载器，全 onnxruntime、不碰 torch |

### 2. 但查开源不替代自己测量

VoiceInk [#687](https://github.com/Beingpax/VoiceInk/issues/687) 那个「间歇性空转录」
至今开着，维护者复现不了。**同一个 bug 我们量出来了**——首次开麦 713ms，句子开头
被吃掉。差别不在聪明，在于我们建了埋点。

### 3. 不要在没有测量的情况下"修"一个假设出来的原因

长句在停顿处切分那次：理论完全说得通（Whisper 看得见句子形状才会打标点），
上线后一测——

```
16.4s 不切 → 4 个标点
24.2s 切开 → 2 个标点
```

**更差，而且慢了五倍。** 已回滚。这条同时违反了第一天就写下的铁律 2
（Whisper 内部把 mel 补到 30 秒，2 秒块和 15 秒块几乎同价）。

### 4. 仪表本身会撒谎，先校准仪表

`last_timing` 的赋值写在 `on_text()` 之后，而报告正是 `on_text` 打印的——
终端上每一块耗时**属于上一句**。一整轮分析是拿「37.8 秒音频」配「11 个字的
转写」做的，两者根本不是同一句。

**排查陷入僵局时，先怀疑自己的测量工具。**

### 5. 会假通过的验证命令，比没有验证更糟

`~/.venvs/utter/bin/pip list | grep torch` 永远打印空——uv venv 不装 pip，
管道 grep 的是空输出。这条命令"验证"了铁律 5 好几次，其实什么都没验证。
正确的是 `uv pip list --python ~/.venvs/utter/bin/python`。

## 二、Whisper / ASR 的坑

### 6. 静音会让 Whisper 凭空编句子

两秒空房间的底噪，Whisper 交出 `"you"` 和 `"Good job."`。**转录前必须过
`vad.has_speech`。** 把编造的句子注入文档，比任何延迟问题都严重。

### 7. temperature 阶梯要有界，但不能取消

原铁律写的是「必须 `temperature=0.0`」（标量）。那样确实把最坏情况从 8–11 秒
压到 1 秒，但漏了一件事：**那条阶梯的用途正是逃出复读循环**。标量意味着无处
可退，模型一旦开始复读就复读到窗口结束（实测收到过同一短语重复五十遍）。

现值 `(0.0, 0.2)`——两级封顶，最坏约 2.2 秒，正常情况零额外代价。
外加一层确定性的 `collapse_repetition` 兜底，且必须**大声报告**折叠了多少处。

### 8. 不指定语言，每句多花约 0.9 秒

多一遍语言检测 encoder。但对中英混说的人，这 0.9 秒是必要开销——
指定 `zh` 会把英文**翻译**成中文，而不是转写。

### 9. Whisper 的中文标点在任何长度上都稀疏

不是 bug，是训练数据的性质（中文语料多为字幕，字幕不带标点）。
配置改不动，只能靠 LLM 润色补，或换模型。

### 10. `initial_prompt` 上限 223 token，超出**从头静默截断**

`n_text_ctx // 2 - 1`。实测 30 条术语表 = 340 字 = 133 token。
超出后最早的词会消失且毫无提示——一个安静失效的术语表。现已在启动时检查。

## 三、模型选型（2026-08-10 实测）

| 引擎 | 英文术语 | 中英混说 | 纯中文 | 速度/每秒音频 | 常驻内存 |
|---|---|---|---|---|---|
| **Whisper turbo 自动** | **全对** | 英文在 | 好 | 90–146ms | 474 MB |
| SenseVoice int8 | 差 | **吞掉英文** | 好，标点更全 | **14–20ms** | 549 MB |
| FireRedASR2-CTC | 中（全大写） | 乱码 | **无标点** | 151–174ms | — |

### 11. SenseVoice 在中文句子里不是听错英文，是删掉英文

> 原话：我这一节想写的是 literature review，大概在 2.1 的位置
> 输出：我这一节想写的是 **re盖** 在2.1的位置

`literature matrix` 整个消失。**中文读着通顺，术语没了**——静默丢失，
事后不会发现。对英文几乎全是术语的使用者，这一条单独否掉它作默认档。

### 12. 文件小 ≠ 占内存小

SenseVoice 权重 228MB 却占 549MB 常驻；Whisper 1.6GB 只占 474MB。
onnxruntime 预分配内存池，MLX 走 Metal 统一内存按需加载。

### 13. 量化不是英文差的原因

同一仓库的 fp32（938MB）与 int8（239MB）返回**逐字相同的错**，且慢一倍。
是模型本身只有 234M 参数。

### 14. SenseVoice-Large 没有开放权重

只在阿里云 API 上。本地不存在"换个大档"这条路。

### 15. provider 抽象是这个项目回报最高的一次投入

换 Whisper → SenseVoice，provider 文件之上**一行没改**。sherpa-onnx 1.13
已内建 Qwen3-ASR / FireRedASR / Fun-ASR-Nano 等二十个加载器，将来出现更好的
模型，接进来只是加一个小文件。

## 四、macOS 集成的坑

### 16. 两个 pynput Listener + 一个 Controller = SIGABRT，无 traceback

pynput 的 macOS 后端从每个 listener 线程进入**不可重入**的 `keycode_context`。
两个 listener 单独没事，加上注入用的 Controller 必崩。**一个进程一个 Listener，
多个 matcher。**

### 17. `Key.alt` 和 `Key.alt_l` 是同一个枚举成员

darwin 后端里两者 vk 相同，Python 的 Enum 把后者变成前者的别名。
右 Option 是 `Key.alt_r`，独立。所以 `<alt_l>` 能工作，但它同时匹配"泛左 alt"。

### 18. `activateWithOptions_` 是异步的

日志说注入到 A，文字落在 B。必须**轮询等到前台真的换过来**再粘贴。

### 19. 剪贴板要在粘贴真正落地之后才还原

25 个单元测试全过，因为它们检查的是最终状态而不是**顺序**。
使用者眼看着之前复制的 shell 命令被贴进文档。

### 20. macOS 有两个都叫「辅助功能」的设置页

一个是功能页（VoiceOver、缩放），一个是隐私里的权限名单，隔一次点击、名字一样。
权限发给**发起进程的那个 app**（终端），不是 Python。改完要 ⌘Q 完全退出再开。

### 21. 蓝牙耳机同时当麦克风，会被拖进通话模式

A2DP → HFP，单声道、低码率、额外延迟。使用者看到的现象是"视频音画不同步、
系统音量变了"，完全不像听写工具干的。代码防不住，只能**不主动触发**
（共用设备时跳过音频预热）并**明说**。

### 22. 忘记退出的 daemon 会安静地毁掉一切

一个 10:26 启动的实例活到 21:30——终端标签早关了，进程还在，
20 个线程、PortAudio 和 CoreAudio 都挂着，**照样抢热键和麦克风**。
按一次键唤醒两个进程去抢同一个设备。从外面唯一的症状是"听写变差了"。
现已加 pid 锁。

### 23. 「advertises input channels」不等于「能录到声音」

测试机上有扬声器、两个虚拟录音设备、一个会议 app 都报告有输入通道，
全都能打开、全都返回纯静默。**`utter mics` 必须真的打开设备录一下**，
光列举 CoreAudio 的回答会把人坑死。

## 五、还没做好 / 已知不足

- **打包**：还是要开着终端跑 `utter dictate`，没有 `.app`（P4）。
- **注入落点**：文字落在**松开热键时**的前台窗口，不是按下时的。使用者已表示暂不修。
- **边说边出字**：还没有（P2b）。而且与铁律 9（注入过的文字永不回改）冲突——
  只能按停顿切句、一句定稿一句注入，代价是润色看不到整段上下文。
- ~~**润色**：从未对着真模型验证过提示词~~ —— 2026-08-10 已验证并接线，见第六节。
  **仍待观察**：守卫会不会误伤（比如模型把英文术语的大小写规范化）。
- **术语表不会自己变好**：手写的静态列表，且有 223 token 天花板。
  `utter vocab add` 和从 Obsidian / Zotero 自动收词都还没做。
- **应用兼容表**：需要在真机上逐个 app 试注入，还没做（P2a Task 7）。
- **听模式（会议记录 + 翻译）**：v1 的 Tauri 界面还在，但走的是旧管线，
  sidecar 链路是断的。P2b/P3 的事。
- **存档只增不减**：实测 227 字节/段、1624 段 = 360 KB 文字。
  因为铁律 3 不存音频，所以增长可以忽略；`utter sessions --prune N` 可手动清。
  同类工具（VoiceInk、Superwhisper）存音频，同样用量一年是几十 GB 级。

## 六、润色（2026-08-10 真模型实测）

### 24. Vertex AI 用云凭据，不需要 API key

使用者有 Google Cloud 额度、没有 Gemini API key。Vertex 收的是 OAuth bearer token，
所以能直接用 gcloud 的凭据。它也有 OpenAI 兼容端点，于是复用现成的 client：

```
https://aiplatform.googleapis.com/v1/projects/{PROJECT}/locations/global/endpoints/openapi
```

实测**不需要** `x-goog-user-project` 头。模型 ID 要带 `google/` 前缀。

### 25. 一台机器上可能有两个 Google 身份，而 ADC 未必是你以为的那个

测试机上 ADC 属于**账号 A**（另一个工具写的，quota 项目是它托管的），
而 gcloud 的活动账号是**账号 B**，后者才是 Vertex 项目的 owner。
**同一个请求：ADC 403，gcloud 凭据 200。**

排查方法（不打印 token）：

```bash
curl -s -X POST https://www.googleapis.com/oauth2/v3/tokeninfo \
  --data-urlencode "access_token=$(gcloud auth application-default print-access-token)"
```

不要贸然 `gcloud auth application-default login` —— 那会**覆盖另一个工具正在用的
ADC**。provider 因此两条都试，谁成谁留。

### 26. Flash-Lite 比 Flash 快 7 倍，输出一模一样

| 模型 | 同一句润色 |
|---|---|
| `google/gemini-2.5-flash-lite` | **980 ms** |
| `google/gemini-2.5-flash` | 6946 ms |

文字逐字相同。润色是简单活，上推理档是花钱买一个提示词整篇都在压制的能力。

### 27. ⚠️ 最重要的一条：提示词禁止不了模型改你的话

铁律 10 的提示词**加粗写着**「不得改写措辞、不得增删内容」。真模型实测：

| 档位 | 实际动作 |
|---|---|
| light | 一字未改，只补标点 ✅ |
| **medium** | 删掉了「呃」**和「因为」** ❌ |
| **heavy** | 把「这个我觉得是」改成「我觉得这个是」❌ |

「因为」是因果连接词 —— 删掉它，一个因果论断变成了并列陈述。
「这个我觉得」变「我觉得这个」是词序改写。

**两个输出都读着非常通顺。** 这正是危险所在：使用者重读一遍不会发现，
而音频已经没了。

于是加了**机械守卫**（`content_signature` / `content_changed`）：
把标点、空白、口水词剥掉之后，润色前后的字符序列必须**完全相同**，
否则整段降级回原始转录并在日志里说明删了什么、加了什么。

这条守卫连「模型帮你改对了」也拦 —— 比如把误听的「规化」纠正成「归化」。
听起来可惜，但铁律 10 没有「改得对就可以」这个例外：一个不能确信文字属于自己的
使用者，只能逐字对着音频重读，而音频已经不在了。

**教训一般化：把规则写进提示词是请求，不是保证。凡是「模型不许做 X」的地方，
都要问一句「如果它还是做了，我能不能机械地发现」。**

### 28. 守卫要「合并」，不要「否决」——否决会把功能整个废掉

第 27 条加的是一个**全有全无**的守卫：内容有变就整段驳回、退回原始转录。
一到真机就失效：

```
polish changed the content (删掉了「那个用那个是哪一个的的但是」), keeping the raw transcript
polish changed the content (删掉了「这个和这个」, 加上了「""""那个"」), keeping the raw transcript
polish changed the content (删掉了「是的然后你看去」), keeping the raw transcript
```

**每一句都被驳回，于是开了润色跟没开一样。** 两个原因叠在一起：

1. **忽略集漏了弯引号 `“ ”`。** 模型极爱加引号，于是「加了引号」被判成「加了内容」。
   教训：这种字符白名单要**宁滥勿缺**，漏一个字符的代价是功能失效。
2. **就算提示词只说补标点，模型还是会顺手删。** 它删了口吃的「的的」、
   删了「是的然后」、甚至删了「但是」。**指令改不掉这个倾向。**

改成 `apply_punctuation(raw, polished)`：**按内容字符对齐两个文本，输出走原始转录
的字符和顺序，只把模型放的标点插进字符之间的空隙**（空隙先过滤成纯标点，
所以模型凭空加的字进不来）。

于是铁律 10 从「一条会失败的检查」变成「构造上的性质」——
输出的内容永远就是转录的内容。模型删的字自动回来，模型改的词序自动复原，
模型答非所问就等于没润色。

顺带一条决定：**大小写也从转录取，不从模型取。** 术语表里有
`van Leeuwen`（全名时 v 小写），模型一定会「纠正」成 `Van Leeuwen`。
句号是收益，大写是猜测。

**一般化：当一个安全检查开始否决绝大多数正常输入时，问题多半不在输入，
在于「否决」这个形状本身选错了。能合并就不要否决。**

## 七、对照开源方案：我们缺什么（2026-08-11）

对照 [VoiceInk](https://github.com/Beingpax/VoiceInk)（macOS 上最成熟的开源同类）
与 [faster-whisper-dictation](https://github.com/bhargavchippada/faster-whisper-dictation)
逐项过了一遍。

### 已经有的

| 能力 | Utter | 说明 |
|---|---|---|
| 本地转录 | ✅ | Whisper turbo / SenseVoice，可换 |
| 按住说话 | ✅ | 左 Option |
| 开关模式 | ✅ | 双击左 Control |
| **边说边出字** | ✅ | 2026-08-11，VAD 分句逐句定稿 |
| 光标处注入 | ✅ | 剪贴板粘贴 + 还原 |
| 术语表 | ✅ | 但**手工维护**，见下 |
| LLM 润色 | ✅ | 而且是**机械保证**不改字，比同类都严 |
| 历史存档 | ✅ | 纯文字，`utter sessions` 可读、可清 |
| 菜单栏 + 开机自启 | ✅ | 2026-08-11 |
| 100% 本地可选 | ✅ | 润色可关，关了完全离线 |

### 缺的（按重要性）

1. **按 app 切配置**（VoiceInk 的 "app detection"）。在 Word 里要正式书面语、
   在终端里要不加标点、在微信里要短句 —— 现在只有一套全局设置。
   **这条对使用者最有用**，因为他在 Obsidian 写论文和在终端敲命令是两回事。
2. **术语表不会自己长**。VoiceInk 有 "Personal Dictionary" 加文本替换。
   我们是一个手写 JSON 列表，还有 223 token 天花板。
   缺 `utter vocab add`，也缺从 Obsidian / Zotero 自动收词。
3. **没有首次运行向导**。VoiceInk 有 onboarding 引导权限与模型下载；
   我们靠 `utter doctor` 加一个启动时的弹窗。
4. **不能分发**。见下节。
5. **没有自动更新**（VoiceInk 用 Sparkle）。对单人自用不重要。
6. **没有应用兼容表**（P2a Task 7）—— 哪些 app 能粘、哪些不能，还没逐个试过。
7. **录音时不暂停音乐**。VoiceInk 有；小事，但每次都要手动按暂停。

### 有意不做的

- **语音助手模式**（VoiceInk 的 "conversational assistant"）—— 这是另一个产品。
- **屏幕内容感知**（"understands your screen content"）—— 要读屏幕，隐私代价太大。
- **99% 准确率这类宣称** —— 本项目的立场是量出来的数字，不是形容词。

### 我们比它们严的地方

**润色的内容守卫。** 同类工具的 "AI enhancement" 都直接采用模型输出。
我们做不到相信它：实测 gemini 和 gpt 在明令禁止的情况下照样删「因为」、
调词序。所以 `apply_punctuation` 只取模型的标点、字一律来自转录 ——
**铁律 10 是构造上的性质，不是一条会失败的检查。**

对一个口述学术论证的人，这个差别不是洁癖：一个读着通顺但论断被改过的句子，
事后不可能发现，而音频已经不在了。

### 29. PortAudio 只在进程启动时枚举一次设备 —— 常驻进程会一直用旧列表

戴上蓝牙耳机后，按热键，连着两次：

```
utterance 0 contained no speech, discarded
utterance 1 contained no speech, discarded
```

daemon 是凌晨 00:12 起的，那时 AirPods 没连，`[1]` 是 Redmi 音箱。
早上 AirPods 连上，系统默认变了、**索引整体挪了位**（`[1]` 成了 AirPods，
Redmi 退到 `[3]`），但**进程里的 PortAudio 还停在旧列表上**。

于是它照着旧索引开了一个已经不对的设备，**录到纯静音、全程零报错** ——
因为「你问了一个没在听的设备」在 CoreAudio 看来不算失败。

这是本项目第三次撞上同一类问题（前两次：`utter mics` 那个「报告有输入通道 ≠ 收得到声音」、
共用设备被拖进通话模式）。**音频设备这一层，任何"启动时读一次"的假设都是错的。**

修法：每次开麦前 `sd._terminate(); sd._initialize()`，实测 **4ms** ——
相对 CoreAudio 开流本身的 240ms 可以忽略，所以不做「聪明地判断硬件是否变了」，
每次都重新枚举。

**一般化：常驻进程和一次性命令的假设不一样。凡是"启动时读一次"的东西
（设备列表、权限、配置、模型 ID），都要问一句"跑三天之后它还对吗"。**

### 30. 菜单栏 app 必须先把图标放上去，再做慢的事

双击 Utter.app，**一分多钟屏幕上什么都没有**，于是说「打不开这个软件了」。
他的判断完全正确 —— 从他能看到的证据出发，只能得出这个结论。

实际发生的：

```
10:29:21  Utter.app starting
10:30:40  model warmed in 77.29s     ← 79 秒的空白
10:30:40  ready
```

`LSUIElement` 的 app **没有 Dock 图标、没有窗口、没有启动反馈**。而我们把三件慢事
全放在了创建菜单栏图标之前：解析语音 provider（要连 Hugging Face）、
等辅助功能授权、预热模型（实测 1.7 秒到 **77 秒**，取决于权重还在不在页缓存里）。

**这三件都不需要主线程。** 改成：拿到锁 → 立刻建 NSApplication 和菜单栏图标
（带一行「启动中…」状态）→ 其余全部丢进后台线程 → 主线程直接进 run loop。
实测**6 秒内图标就在了**，而且菜单里写着它正在干什么。

外加就绪时发一条通知横幅，和一条 `utter status` 命令 ——
「我看不到图标」和「它没在跑」必须能区分开，而不是都表现为「什么都没有」。

**一般化：GUI 程序里，"先干活再画界面" 永远是错的顺序。**
用户对「没反应」的默认解释是「坏了」，而且这个解释通常是对的 ——
只有在你把反馈做出来之后，它才变成错的。

### 31. `exec` 出去的 .app，LaunchServices 不认它启动完成

图标不出现，查了一个小时，最后是两个独立的原因叠在一起。

**原因一（我自己上午引入的）：菜单每次重画都在重启 PortAudio。**

早上修「戴上耳机不切换」时，我把 `refresh_devices()`（`sd._terminate()` +
`sd._initialize()`）放进了 `shared_with_output()`。而菜单栏的告警行每次
`_rebuild()` 都会调它 —— 于是**启动过程中整个 CoreAudio 连接被反复拆了又建，
就在主线程上**，状态项因此从来没被布局过。

`isVisible()` 一直返回 `True`，`frame` 却是 `32×0` 停在原点。
**「可见」和「有位置」是两件事**，而只有后者决定你能不能看见它。

**原因二：启动器用 `execv`。**

`Contents/MacOS/Utter` 是个 C 小程序，`execv` 成 Python。这让进程号不变、
`CFProcessPath` 也保住了 bundle 身份（权限归 Utter 而不是 Python），
看起来很干净 —— 但 **LaunchServices 启动的那个可执行文件已经不存在了，
它永远等不到「应用启动完成」**。

结果是个非常刁钻的现象：
**同一个二进制，从终端跑图标正常，`open` 打开就没有。** 其他一切都正常
（热键、权限、日志、AX 树里能查到菜单项），只有布局不发生。

改成 `posix_spawn` 一个子进程再 `waitpid`：父进程留在原地当
LaunchServices 认识的那个 app，Python 作为子进程跑（子进程的处境和"从终端跑"
一样，而那是可行的），并转发 SIGTERM/SIGINT 保证退出时不留孤儿。

**一般化两条：**
1. **别把「顺手做点新鲜事」塞进每帧都会跑的路径。** 一个 4ms 的设备重枚举，
   放在开麦前是对的，放在菜单重画里就毁了启动。
2. **`.app` 的主可执行文件不要 exec 走。** 包装式启动器必须留在原地。

### 32. 麦克风权限看代码签名，`CFProcessPath` 骗不过它 —— 而被拒时它给你静音，不给你报错

按热键，日志说「没听到」。加了诊断之后：

```
设备=AirPods Pro  时长=6.5s  峰值=0.0000  ← 纯静音
```

**恰好为零，持续 6.5 秒。** 安静房间的真麦克风也会有约 0.001 的底噪，
**精确的 0 不是安静，是 macOS 在拒绝。** 而它拒绝的方式是**一直给你静音，
不报任何错** —— 打开流成功、回调正常、每一帧都是 0。

原因：`.app` 的启动器指向 `~/.venvs/utter/bin/python`。
`CFProcessPath` 能让 CoreFoundation 认为进程属于这个 bundle（辅助功能因此归了
Utter），但 **TCC 判的是代码签名**，而那是个在 bundle 外面的 anaconda 二进制。
麦克风申请**一毫秒返回 refused，连弹窗都没有**。

实测矩阵（这两件事互相独立，我一度把它们混在一起）：

| | 菜单栏图标 | 麦克风 |
|---|---|---|
| `exec` 到外部 python | ❌ | ❌ 秒拒 |
| `spawn` 外部 python | ✅ | ❌ 秒拒 |
| **`spawn` bundle 内的 python** | **✅** | **✅ 弹窗并授权** |

解法：**把解释器复制进 `Contents/MacOS/python`，和 bundle 一起签名。**
它是静态链接的（`otool -L` 只有 libSystem），5.6MB，靠 `PYTHONHOME` 找标准库、
`PYTHONPATH` 找 venv 的包。这样发出麦克风申请的那个进程**就是** Utter。

**一般化：包装式 .app 想拿到权限，真正运行的那个二进制必须在 bundle 里、
并且被一起签名。任何"让系统以为我是它"的技巧，在 TCC 面前都不成立。**

顺带记一条排查心法：**精确的 0 值几乎不是物理量，是拒绝。**
真实传感器有噪声；一列完美的零来自软件里的某个 `if`。

### 33. Whisper 会在静音里编出「字幕志愿者」，而且它进了文档

存档里翻到的：

```
转录: 字幕志愿者 李宗盛。
```

**没有人说过这句。** Whisper 的中文训练数据大量来自视频字幕，没东西可转录时它就
去够片尾字。VAD 门槛是第一道防线、也确实挡住了大部分，但它回答的是
「有没有人在说话」，不是「这段输出是不是真的」—— 一声咳嗽就够给模型一个开口。

`is_hallucination()` 只丢**整句都是套话**的输出。第一版写成了「包含套话 + 长度上限」，
那样会丢掉

> 这一节我要讨论字幕志愿者这个群体在数字人文里的位置

这恰恰是使用者会说的句子。**丢掉他真说过的话，比放过一句假话严重得多（铁律 8）**，
所以改成「把套话都剥掉，看还剩多少」：幻觉剥完几乎什么都不剩，真句子剥完还是句子。

### 34. `load()` 永不失败 + 有人接着 `save()` = 永久丢数据

使用者发现「大语言模型」被听成「大圆模型」。这是**转录**错误，润色按设计不会碰它
（`apply_punctuation` 的字一律来自转录）。修法在上游 —— 加进术语表。
结果一打开发现**术语表只剩 7 条，原来的 30 条没了。**

机制比这一次事故重要。`load()` 被刻意设计成永不失败：**打不开 app 的人，
也没法用 app 去修那个让它打不开的设置**。但「永不失败」意味着它返回默认值，
而任何**接着写回去**的调用者，就把一次临时的读取问题变成了永久丢失 ——
`_save_config` 每次点菜单都在做这件事。

于是加了 `load_or_none()`：文件存在但读不了时返回 None，写入方看到 None 就
**不写**。一个菜单开关的价值低于那个文件。`_load_field_by_field` 也改成
**说出它丢了哪些字段**，不再默默丢弃。

**一般化：「宽容地读」和「照读到的写」是两个策略，凑在一起就是数据丢失。
凡是 read-modify-write，中间那个 read 必须能说「我没读好」。**

### 35. 流式的标点：让说话人的停顿来决定，不要让模型猜

同一件事我连着做错了两次，方向相反：

| 做法 | 结果 |
|---|---|
| 每个小句都补句号（照搬"按住说话"） | 但是这个延迟。好像。还是比较多的。 |
| 一个都不补（上一条的过度修正） | 但是这个延迟好像还是比较多的 |

两次都是在**猜句子在哪里结束**。而这个问题**说话人已经回答过了 —— 他停顿了**，
VAD 也把那个停顿量下来了。

改成：**短停顿（<800ms）给逗号，长停顿给句号，会话结束给句号，
Whisper 自己已经打了标点就不动。** 不涉及任何模型，也没有任何内容被发明 ——
只加了一个标点，这是铁律 10 一直允许的。

没有停顿数据时（一段话的第一个小句）取逗号：**逗号后面还能接，句号收不回来**
（铁律 9）。

**一般化：在为「模型答不出的问题」加一层猜测之前，先问一句——
这个信息是不是已经在别处被测量过了。** 停顿长度一直躺在 VAD 的输出里，
而这里却先后写了两版猜测。

### 36. CALayer 的背景色不跟随浅色/深色，NSColor 跟随

设置窗口的分组卡片原本是 `NSView` + `layer.backgroundColor = 白色 5% 透明`。
在深色桌面上好看，**在浅色模式下整张卡片消失** —— 白色叠在白底上。

原因不在于颜色选错了，而在于 `CALayer.backgroundColor` 收的是 `CGColor`，
**`CGColor` 就是一组固定的数字**，没有"语义"，系统切主题时它不会变。
`NSColor.controlBackgroundColor` 是语义色，AppKit 会在外观变化时重画。

改用 **`NSBox`**（`boxType = Custom`、`fillColor` / `borderColor` 给 NSColor、
`cornerRadius`）后两种模式都对，且不需要监听外观变化通知。

**一般化：凡是手写十六进制或 RGB 的颜色，都是在替系统做一个它每天都会改的决定。
自绘一层之前先找有没有对应的语义色。**

### 37. "排版均匀"是边距的性质，不是控件的性质

前一版给每个控件算了同一个宽度（`CONTROL_W = 窗口宽 - 边距 - 标签列 - 间隙`），
右边缘确实全部对齐了 —— 然后「润色」那一栏出现了一个 **382pt 宽、里面只有一个
「关」字的下拉框**。为了对齐而对齐，比不对齐更显眼。

Apple 自己的表单是**两端锚定**：标签贴左边距，控件贴右边距，控件各自保持自然宽度。
「中文」就是窄的，模型名就是宽的，右边缘照样齐。

顺带一个 Auto Layout 的坑：`NSStackView` 的 `alignment = .width`
**不足以**把子视图撑满 —— 三张卡片里有一张自己缩到 336pt（另外两张 460pt），
因为对齐约束打不过卡片自身内容的约束。**把宽度直接写出来
（`子.widthAnchor == 栈.widthAnchor`）才每次都对。**

**一般化：先问"这条边应该落在哪"，再问"这个控件该多宽"。顺序反了就会为了
对齐而把控件拉成畸形。**

### 38. 测试套件改掉了使用者的真实配置——而且是第二次

使用者早上打开设置窗口，发现**润色档位是「重」**。他从没选过重。

追下去：`backend/tests/test_daemon.py::test_changing_the_level_rebuilds_too`
里有一行 `d.set_polish(True, "heavy")`。`set_polish()` 会持久化——**这是对的，
也正是那个测试要验证的行为**——于是它调 `_save_config()`、调 `save()`，
而 `save()` 的 `base_dir` 默认取 `DEFAULT_DIR`，也就是真实的 `~/Utter`。

**跑一次 `pytest`，使用者的实际设置就被改一次。** 同一次污染还把
`stream_while_speaking` 也翻了。

这些测试单看没有一行是错的。错在**被测对象是用真实默认值造出来的**，
而真实默认值里就有真实路径。测试没有"我在沙盒里"这个概念，daemon 也没有。

修法是把沙盒变成**默认**，而不是靠每个测试记得申请：`backend/tests/conftest.py`
里一个 autouse fixture 把 `DEFAULT_DIR` 指到每个测试自己的临时目录；真的要测
默认路径的用 `real_utter_dir` fixture 显式退出。另加
`test_config_sandbox.py` 守护这个守护——autouse fixture 是隐形的，
重构时删掉不会有任何测试变红。

**这是第二次了。** 第一次是丢了 30 条术语表词条，当时修的是
`load()` 读不到就返回默认值那个点（加了 `load_or_none`）——**修了那一个症状，
没修这一类**。相隔两天，同一个机制换个入口又咬了一口。

**一般化：一个 bug 修完要问"这是哪一类的一个实例"。只修实例，
下一个实例就在路上。** 具体到测试：**凡是被测代码会写盘，
沙盒必须是默认值，不能是可选项。**

### 39. `from X import Y` 会把值复制走，于是沙盒漏了一半

第 38 条给测试加了沙盒：autouse fixture 把 `config.DEFAULT_DIR` 指到临时目录。
配置文件确实不被污染了。**但连用一天后去看存档，里面躺着 1299 个 session 文件，
其中一千多个是测试产生的**，和真实口述混在一起。

两处都是**导入期绑定**：

```python
# config.py —— 类定义时就求值，真实家目录被烤进了类里
save_dir: str = str(DEFAULT_DIR / "sessions")

# scratchpad.py —— 拿到的是值的副本，之后再 patch 模块属性也够不着它
from backend.config import DEFAULT_DIR
```

`from X import Y` 建立的是**新名字绑定到当时那个值**，不是对 `X.Y` 的引用。
后来 monkeypatch `X.Y`，这个副本纹丝不动。

改成 `save_dir: str = Field(default_factory=lambda: ...)`（实例化时才求值）
和 `from backend import config` + `config.DEFAULT_DIR`（调用时才读）。

**一般化：想让一个值可以被替换，就不能在导入期把它取出来。** 而且——
**修完一类 bug 要去找这一类的其它实例**。第 38 条自称修的是"一类"，
实际上只覆盖了配置文件，旁边的存档一直在漏，两天后才被真实使用暴露出来。

### 40. `if x:` 没有 `else`，就是一条无声失败的路

一天 115 次按键，105 次出字，7 次报告"没听到"。**剩下 3 次什么都没有——
没有文字，没有警告，没有一行日志。**

```python
chunks = list(mic.chunks())
if chunks:
    self._enqueue(...)
# 没有 else
```

麦克风一帧都没交出来的时候，这次按键就凭空消失。讽刺的是，
下游"音频里没有语音"那条路报得极细（设备、时长、峰值——第 34 条的产物），
唯独**"连音频都没有"这条更靠前的路一句话都不说**。
麦克风冷启动实测到过 713ms，按得够短就会命中。

**一般化：在一个以"绝不静默丢失"为纲领的程序里，每一个没有 `else` 的 `if`
都值得问一句——走另一条路的时候，用户怎么知道？** 而且这类洞
**测试很难发现，因为它的症状就是"什么都没有"**；它是被一天的真实使用
和一次日志对账（按键数 vs 产出数）逼出来的。**该做对账。**

### 41. 单元测试全绿，因为它们测的是我以为模型会返回什么

听记的翻译要批量发（一次 3 句，省下 90 分钟会议里的四百次请求）。批量引入了
一种新的错法：**回来的行数如果对不上，第 12 句的中文会挂到第 11 句的英文下面**，
而两行看上去都是好句子，根本发现不了。

所以我给每行编了号，回来按编号认领，还专门写了 7 个测试覆盖各种错位——
少一个号、多一个号、重复号、完全不带号。**全绿。**

然后拿真模型跑第一次，翻译一条都没出来：

```
翻译回来的内容对不上编号，这一批保持未翻译
```

去看模型到底返回了什么：

| 发出去 | 收回来 |
|---|---|
| 3 行带编号 | **3 行带编号**，完美 ✓ |
| 1 行带编号 | `因此，等值问题其实根本不是一个关于词语的问题。` ✗ |

**只有一句时，模型认为编号是多余的，直接把它去掉了。** 这个行为很合理——
换成人也会这么做。而**一句的批次在实际使用中到处都是**：等待超时的刷新、
每次暂停、结束时的最后一次刷新。也就是说，**每场会议的最后一句都会丢译文**。

修法不是把提示词写得更严，而是**取消这个批次的对齐需求**：批次里只有一句时，
整个回复就是那句的译文——**一个条目根本没有东西可以错位**。

**一般化：涉及模型返回格式的测试，只要 fixture 是我自己写的，
它验证的就是我的假设，不是模型的行为。** 这类测试有价值（错位逻辑确实是对的），
但**必须配一次真模型的往返**，否则绿灯是假的。

顺带一提：**那个守卫是对的**。它没有把中文错挂到别的句子上，而是明确说
"对不上编号，这一批不译"。**明确失败让我十分钟就定位了；静默错位可能要等到
某天读记录时才发现，甚至永远发现不了。**

### 42. 系统音频：两个"看起来成功了"的陷阱

macOS 14.4 起的 Core Audio Taps 让抓系统声音不再需要装 BlackHole 那类虚拟声卡。
纯 Python（pyobjc）就能走通，零新依赖。但**这套 API 文档极少，每一步都有一种
"看起来成功了"的失败方式**，2026-08-16 逐步实测踩到两个：

**陷阱一：字典的键必须是 CFString，pyobjc 给的是 bytes——直接段错误。**

建聚合设备要传一个 CFDictionary。pyobjc 把那些键常量暴露成 `bytes`
（`b'name'`、`b'uid'`），照着传下去**解释器当场崩掉：没有异常、没有报错、
没有任何输出**。我第一次跑的时候整个命令零输出，一度以为是命令写错了。

`.decode()` 一下就好了。**但零输出的崩溃比任何报错都难查**——
下次遇到"什么都没打印"，先怀疑是不是把 bytes 当字符串传进了 C API。

**陷阱二：PortAudio 会假装帮你重采样，然后返回一片精确的零。**

设备是 48kHz 立体声，管线要 16kHz 单声道。最省事的做法是让 PortAudio 转：

```
sd.check_input_settings(device=idx, channels=1, samplerate=16000)  # 通过 ✓
sd.InputStream(...)                                                # 开了 ✓
收到 2.81s @16kHz 单声道，峰值 0.0000                                 # ✗
```

**这正是本项目最老的那条教训换了个地方出现**：一列完美的零永远不是测量值，
是某个软件里的 `if`。老老实实按设备原生格式打开、自己转，才有声音。

顺带一条设计发现：**默认全局 tap 是错的**。实测时全局 tap 把用户另一个窗口里
正在播的视频也录了进来，转录结果里混着 `why do you think my husband has
anything to do with it` 这种句子。改成**只录指定程序**（先把 pid 翻译成
Core Audio 的进程对象，再用 `initMonoMixdownOfProcessesIDs_`）后，
转录干净了——**而且这同时是个隐私改进**：不再录下用户碰巧在放的任何别的东西。

### 43. 一个下划线让按钮彻底失灵，而且不报错

听记页做好后，作者报告"点开始没反应，还卡"。查出来是两件事叠在一起，
**其中一件是一个字符**。

```python
# 我写的
AppKit.NSButton.buttonWithTitle_target_action_("开始听记", delegate, "toggle_")
# 该写的
AppKit.NSButton.buttonWithTitle_target_action_("开始听记", delegate, "toggle:")
```

`toggle_` 是 Python 的方法名，`toggle:` 才是 Objective-C 的选择器。
传前者等于把按钮接到一个**不存在的方法**上。点下去抛
`unrecognized selector`，而这个异常**在 AppKit 的事件循环里被吞掉**——
界面上什么都不会发生，日志里也没有一行。

讽刺的是本项目其它十几处 action 全都写着冒号（`"openWindow:"`、`"pickModel:"`），
只有新写的这处顺手写成了 Python 名。**同一个文件里正确的写法就在上面几行。**

**第二件事是卡顿**：点击处理函数里直接加载了模型、打开了音频设备——
全在界面线程上。**几秒钟的冻结，看起来就像"按钮没反应"**，
和第一件事的症状一模一样，所以一开始分不清是哪个。改成后台线程 +
按钮显示「正在准备…」。

**一般化：GUI 里"点了没反应"至少有三种完全不同的原因**——
没接上（选择器错）、接上了但被吞了（异常）、接上了但在阻塞（主线程干重活）。
**它们症状相同，必须分别验证**：我先用 `performClick_` 确认了触发与否，
才知道该修哪一个。

**还有一条**：作者同时指出「线上会议/线下会议」这种分类是错的——
那是要用户把"我的场景"翻译成"设备"。**直接列系统当前真实有什么**
（麦克风逐个列出、能做系统音频才显示系统音频），不存在的不要编。

### 44. 「点了没反应」的第三种成因：异常被 AppKit 吞掉

第 43 条讲了选择器写错。修完之后作者说**还是点不动**——而且日志里依然一个字都没有。

第二次的原因不同：按钮**触发了**，然后在 `window.set_preparing(...)` 上抛
`AttributeError`——那个方法我加在了「页面」类上，忘了从「窗口」类转发。
**而 AppKit 把动作处理函数里的异常整个吞掉**：不进日志、不进控制台、
界面上毫无迹象。症状和选择器写错**一模一样**。

两次都是同一个根问题：**GUI 动作里的异常默认是隐形的。**
所以修法不是再修一个实例，而是给所有动作处理函数加一层网：

```python
def guarded(fn):
    def wrapped(self, sender=None):
        try:
            return fn(self, sender)
        except Exception:
            log.warning("界面动作 %s 出错", fn.__name__, exc_info=True)
    return wrapped
```

**一般化：凡是框架替你调用的回调（GUI 动作、通知、定时器、音频回调），
都要假设它吞异常，并自己兜住。** 否则一个拼写错误就等于一个无法诊断的
"功能不存在"。

### 45. 系统录音权限：又一次「给零，不报错」

界面终于能点了，听记也起来了，**但记录还是空的**。日志里
`系统音频已打开：设备 6，48000Hz 2声道` ——一切正常，就是没有声音。

原因：**打包后的 app（`com.dylan.utter`）没有「系统录音」权限**。
我之前所有实测都是从终端跑的，继承的是终端已有的授权，所以一路都通。

**macOS 在缺这个权限时不报错、不弹窗，只是让 tap 一直返回零** ——
和麦克风权限完全同一个模式（第 x 条）。**这是本项目第三次撞上"完美的零"。**

所以现在：录了几秒还是零，就明确弹窗说是权限问题，并直接给一个
「打开设置」按钮跳到那个面板。**判据是"零 vs 极小"**——真实的安静房间
或没人说话的会议是 0.0001 量级，**精确的 0 只可能是软件里的一个 `if`。**

**一般化：每接一个新的系统音频/视频源，都要先问"没权限时它怎么表现"。
在 macOS 上答案通常不是报错，而是静默的零。**

### 46. 听记沿用了听写的分段参数，于是每 30 秒才出一次字

第一次真实试用（一场英文演讲，系统音频），作者说"太慢，哪怕延迟 2 秒都没做到"。
翻记录，10 条条目，每条 380–495 字，**间隔 26–30 秒**——全部撞在
`max_utterance_sec=30` 的上限上。

原因很直白：听记直接用了 `vad_silence_ms=600`，而**那个数问的是
"这段话说完了吗"**。讲者演讲时根本不会停 600 毫秒，所以 VAD 永远等不到
静音，只能靠 30 秒硬上限切。**每 30 秒的音频 + 3 秒转录 = 33 秒才出一次字。**

讽刺的是**这个教训项目里已经有了**：P2b 做边说边出字时量过同一件事，
结论写在 config 里——600ms 问"说完了吗"、400ms 问"这句断了吗"。
**听写学到的东西没有传给听记。**

改成听记专用的 `listen_silence_ms=500` / `listen_max_seconds=12`。

**一般化：参数是跟着"它在回答什么问题"走的，不是跟着模块走的。**
同一个 VAD、同一个门限值，在两种模式里回答的是不同的问题，就必须是两个数。
复用参数名比复用代码更容易出错，因为它看起来对。

### 47. 复读循环进了记录，而且被忠实地翻译了出来

同一次试用，一条记录里出现「既的」连续重复 68 次，136 个字符——
**而译文把整段复读原样译成了中文**。

铁律 1 早就写着这是 Whisper 的已知失败模式，`collapse_repetition()`
也早就写好并在听写里用着——**听记的管线单纯没调用它**。

更值得记的是：**置信度抓不到这个**。那一条 `avg_logprob = -0.147`，
稳稳落在健康区间（本次实测正常语音 -0.09 ~ -0.18）。模型对自己复读的内容
非常有信心。所以这道防线**必须是结构性的**，不能靠打分。

顺带这次拿到了真实的置信度分布：**正常 -0.09 ~ -0.18，最差的一条 -1.09**。
终于可以定阈值了——但要记住它挡的是"听不清"，不是"复读"。

### 48. 分句只有一个阈值是不够的：换气和句号长得一样

第 46 条把听记的静音阈值从 600ms 降到 500ms，解决了"每 30 秒才出一次字"。
**然后立刻掉进了对面的坑**：25 条记录、中位 23 个字，只有一半是完整句子——

```
「My father」  「from equity states」  「有没有」  「symbols, dreams」
```

原因是**一个阈值回答不了两个问题**。讲者在词组之间换气也是 500ms，
在句子之间停顿也是 500ms，光看静音长度分不出哪个是逗号哪个是句号。

加**下限**才分得开：`min_utterance_sec=4.0` —— 停顿只有在已经积累了几秒语音
之后才允许结束一段。合成对照实测（词组间停 600ms、句子间停 1.2s）：

| | 段数 | 长度 |
|---|---|---|
| 只有 500ms 阈值 | 5 段 | 1.3s / 1.7s / 1.7s / 1.7s / 1.4s |
| 加 4 秒下限 | **2 段** | **5.6s / 5.0s** |

上下限一起把延迟夹住了：**不会短于一句，也不会等过 12 秒**。

**一般化：先问"这个参数在回答什么问题"，再问"一个数够不够回答它"。**
两次调整都只动了一个旋钮，两次都从一个极端荡到另一个极端——
因为真正的判据（这是逗号还是句号）根本不是单一维度的。

### 49. 一条隐形的约束把窗口钉死了

「开始听记就收成书签」写完之后不生效：标签栏藏起来了，**窗口纹丝不动**。
说明代码跑到了，只是 `setFrame` 没效果。

原因在另一个页面上：设置栏有一条 `width == 460` 的固定约束。
**即使那一页是隐藏的，约束仍然生效**，于是整扇窗有了 500pt 的下限，
而书签要 360pt。Auto Layout 不会报错，只是安静地不让你变。

改成让设置栏跟随页面宽度（左右各留边距），窗口立刻能收：500 → 360 → 复原 500。

**一般化：`setFrame` 没反应时，先找是谁在约束它——而不是怀疑 setFrame。
隐藏的视图仍然参与布局。**

### 50. 修好一处延迟，把另一处放大了三倍——因为两个参数是耦合的

第 48 条把听记的分段从"每 2.5 秒一条碎片"改成"每 5–12 秒一个完整句子"。
转录延迟修好了。**然后作者说"翻译太慢"。**

原因不在模型，在我：翻译队列是**攒够 3 条才发**（`BATCH_SIZE=3`）。
那个数字是在条目每 2.5 秒来一条的时候定的——攒 3 条约 7 秒，合理。
**条目变成 5–12 秒一条之后，攒 3 条就是 15–36 秒。**

**我改了 A，而 B 的取值本来就依赖 A，却没跟着改。** 分段和批量之间有一条
没写下来的关系：*批量 × 条目间隔 = 翻译前的等待*。两个参数各自看都合理，
乘起来才是用户感受到的东西。

改成一条一发、最多等 1.5 秒。代价是请求数变多（一小时约 450 次），
上文仍然带前两条，所以质量不受影响。

**一般化：调一个参数之前，先问"有没有别的参数是按它的旧值挑的"。**
配置项之间的耦合不会出现在任何一个参数的注释里，只会出现在用户的体感里。

### 51. 长文档的 TextKit 默认全量重排

作者反复说"卡顿、调整窗口大小不丝滑"。先量了追加一条的耗时——
10 条和 200 条都是 0.5ms，**不是它**。再量改窗口大小：

| | 150 条（1.9 万字） | 400 条（5 万字） |
|---|---|---|
| 默认 | 11–21 ms | 更慢（随长度涨） |
| `allowsNonContiguousLayout = True` | **6.6 ms** | **5.0 ms（不涨）** |

NSTextView 默认**每次宽度变化都重排整个文档**，而会议记录只会越来越长。
打开非连续布局后只排可见部分，**耗时变平**——400 条和 150 条一样快。

**一般化：先量哪一步慢，再修。** 我一开始以为是追加文本或 GPU 争用，
两个都猜错了；真正的开销在一个我没想到的地方，而且一行就能修。

### 52. 答案一直在文本里，我却一直在音频里猜

听记的断句我调了两轮，两轮都荡到极端：600ms → 每 30 秒一大块；
500ms → 「My father」这种碎片。第三轮加了 4 秒下限，好一些，但作者仍然说
"要么太短要么太长"。

**因为我一直在问错的信号。** 讲者在词组之间换气和在句子之间停顿，
长度是一样的——**静音时长里根本没有"这是不是一句话"这个信息**。

而 Whisper **已经把答案给了**：它输出带标点的英文。本项目 08-12 甚至量过
——4 句话 6 个标点、专有名词完整。**我量过它、写进了教训、然后继续用静音猜。**

改成：VAD 只负责廉价地找"某个边界"，**句子从文本里切**——按标点断句，
一块结尾没说完的话留着，接到下一块前面。实测：

```
转录块: ["The people there are warm,", "grounded and strong. My father",
        "came from a quiet state", "in the southwest. It shaped him."]
→ The people there are warm, grounded and strong.
→ My father came from a quiet state in the southwest.
→ It shaped him.
```

查了同类做法后确认这就是流式翻译的标准形状：**切分由标点引导、用前文作上下文**，
而硬性按音频切分是公认的错误来源。**我自己摸索了三轮，别人早写在综述里。**

顺带一个测试抓到的坑：判断缩写不能用 `endswith`——
**「southwest.」以「st.」结尾**，于是整句被当成缩写吞掉。必须按词边界匹配。

**一般化：调参数调到第三轮还在两个极端之间荡，说明用错了信号，
不是参数没调好。** 停下来问一句"我要的信息真的在这个信号里吗"。

### 53. 「拖动不丝滑」的真相是根本没有可拖的边

使用者说「不能丝滑的拖动大小」。这句话的措辞把我引向性能：我去量了 300 条
转录时的重排耗时（13.8ms，够快），又去量了设置页（0.9ms）。两处都不慢。

真正的原因在第三次测量才露出来：

```
styleMask resizable = False
```

窗口是当年作为**设置窗口**建的，而设置窗口按 macOS 惯例就是不可缩放的——那时
这个判断是对的。后来它多了一个页面，装进了实时转录，于是它变成了一个**阅读窗口**，
而阅读窗口不可缩放是荒谬的。没有人回头改那一行 styleMask。

教训有两层。一是**症状的措辞不是诊断**：「不丝滑」听起来像帧率问题，实际是能力
缺失，用户只是没有别的词来形容「拖不动」。二是**窗口的性质会随着装进去的东西改变**，
而 styleMask 这种一次性写好的东西不会自己跟着变。

顺带定了最小宽度：不是拍脑袋的数，是量出来的——三个独立按钮的工具条要 381pt，
书签只有 368pt，而 NSStackView 遇到放不下时的反应是**裁掉一个视图**，被裁掉的
可能正是「结束」。于是改成一个 Aa 下拉（263pt），最小宽度锁在书签宽度。

### 54. 权宜之计没留记号，于是它活成了正式设计

`listen_min_seconds = 4.0` 是在**分句还没做出来**的时候加的：那时候按静音切句，
500ms 的停顿会把「My father」这种半句切出去，所以加了个下限硬扛。

后来第 52 条做了从标点分句，碎片问题从根上没有了。但没有人回去删那个 4.0，
于是它从「防碎片」悄悄变成了「每句话强制多等 2.5 秒」——使用者感觉到的「慢」，
一大半是它。量出来的模型耗时其实很正常：转录 1.1–1.3s、翻译 0.9s。

**权宜之计要在代码里写清楚它在替谁顶班**，否则等正主到位时没人认得出它该退场。
