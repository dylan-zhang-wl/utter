# P2a 听写延迟实测（2026-08-10）

机器 Apple M2 / 16G，`mlx-community/whisper-large-v3-turbo`（均衡档）。
目标：不开润色 ≤1500ms。

## 结论：达标，但有两个坑是只有真机跑才暴露的

| 按住时长 | 合计延迟 | 判定 |
|---|---|---|
| 2s | 1041 ms | ✅ |
| 4s | 968 ms | ✅ |
| 8s | 1053 ms | ✅ |

启动预热 3.3s（一次性，把 P1 记录的"第一句 2.76s"移出了用户路径）。

## 坑一：自动语言检测让延迟翻倍

8 秒音频，各测 3 次取中位：

| 设置 | 耗时 |
|---|---|
| `language="en"` | **1067 ms** |
| `language="zh"` | **1057 ms** |
| `language=None`（自动检测） | **1927 ms** |

**差额 860ms 是 Whisper 为了猜语言额外过的一遍 encoder。** 它比整个延迟预算的一半还多，
自动检测状态下无论如何撞不到 1500ms 目标。

配置项 `dictate_language` 默认仍是 `None`——作者中英双语写作，猜错语言比慢一点更糟——
但 `utter dictate` 启动时会明说这个代价。**作者确定某次是单语口述时，设一行配置省一半延迟。**

> 排查过程记一笔：最初怀疑是 pynput 的事件监听线程抢 CPU（macOS 事件 tap 跑高优先级 runloop）。
> 对照实验证否——有无监听器都是 1070ms。**不要凭直觉归咎于最可疑的组件。**

## 坑二：对着静音按热键，Whisper 会凭空编出句子

实测：房间无人说话时按住 2.5 秒，转录结果是 `"you"`，第二次是 `"Good job."`。

按住说模式的分段器是手指，不经过 VAD，所以这个洞一直开着。
**往作者文档里注入一句它自己编的话，是本项目能犯的最严重的错误**——比任何延迟问题都严重。

修法：转录前先用 silero 过一遍（`backend/vad.py: has_speech`）。代价 1–136ms，
静音时直接丢弃、模型根本不启动：

```
  hotkey → buffer closed          3 ms
  speech check                  100 ms
  transcription            (no speech)
  ────────────────────────────────────
  total                         103 ms      ← 而不是 1956ms + 一句假话
```

## 坑三：PortAudio 关流 130ms 挡在关键路径上

拆解 `end_utterance`：排空队列 0.1ms，拼接数组 0.1ms，**关闭音频流 130.6ms**。

改成先取音频入队、再异步关流后，`hotkey → buffer closed` 从 119ms 降到 **3ms**。

## 热键：右 Option 单键

按住 350ms 测得 334ms，开销约 8–16ms。左 Option 正确不触发。

pynput 有两个坑：`HotKey.parse("<alt_r>")` 产出裸键码而监听器报 `Key.alt_r`，两者永不相等；
且 `canonical()` 会把 `Key.alt_r` 折叠成 `Key.alt`。都已在 `backend/hotkey.py` 绕过。

## 剪贴板保真

五种 flavour（纯文本 / RTF / HTML / 二进制 PNG / macOS 派生的 UTF-16）写入再还原，
**逐字节一致**。铁律 12 的"粘完还原"成立。

## 坑四：中英混说时，Whisper 会把中文「翻译」成英文

作者实测（2026-08-10）：一整句英文学术论述后面接一句中文提问「这句话是什么意思呢？」，
自动检测档下输出成了 `This is what means?`——**中文被翻译了，不是转录**。

原理不是 bug 而是结构：**Whisper 每 30 秒窗口只带一个语言标签**。前段英文占主导，
检测判定为英语，解码器就被约束在英语 token 上；听到中文时它无法输出中文，
只能"用英语说出来"。第二次测试中英穿插较均匀，检测结果不同，两种语言就都保住了——
**这也说明自动检测的结果依赖哪种语言占主导，不稳定。**

固定语言实测（13 秒纯英文素材，含 Venuti 等术语）：

| 设置 | 耗时 | 纯英文结果 |
|---|---|---|
| `language="en"` | 1123 ms | 正确 |
| **`language="zh"`** | **1155 ms** | **正确** |
| `language=None` | 2031 ms | 正确 |

**`zh` 是严格最优解**：中文不被翻掉、英文术语照常保留、省掉 880ms 检测开销。
唯一代价是句号后不加空格（中文排版习惯），润色档可补。

`dictate_language` 默认值因此从 `None` 改为 `"zh"`。**这是为本作者的双语使用场景选的，
不是普适默认**——纯英语用户应设 `"en"`。

> 与 P2b 的关系：设计 §9 待决 3 原本就排了「中英混说用哪档模型」的实测。
> 这条给它加了一个具体判据——**候选模型必须在句内语码转换上不做翻译**。
> SenseVoice 宣称中英混说更强，值得优先比。

## 坑五：铁律 1 的标量 temperature 导致复读死循环

作者实测（2026-08-10）：一次 26.9 秒的口述，输出是 `of the model sign` **重复约五十遍**。

根因在 Whisper 的解码循环里：

```python
if decode_result.compression_ratio > compression_ratio_threshold:
    needs_fallback = True  # too repetitive
```

**那条 temperature 阶梯的用途，正是检测并逃出复读。** P1 为了延迟把它设成标量 `0.0`，
阶梯只剩一级——**检测照常触发，但无处可退**，于是循环跑到窗口结束。

也就是说，铁律 1 把「偶尔慢 8 秒」换成了「偶尔吐出五十遍同一句」。后者严重得多。

修正为两级 `(0.0, 0.2)`，并关掉 `condition_on_previous_text`（它把一个窗口里开始的复读
喂进下一个窗口，是循环自我强化的通道）。正常情况零额外代价：

| 音频长度 | 有界阶梯耗时 | 最高词频 |
|---|---|---|
| 3s | 951 ms | 1 |
| 8s | 1050 ms | 3 |
| 27s | 1393 ms | 6 |

第二级只在第一级产出退化时才跑，最坏情况约 2.2 秒。

## 坑六：中文标点靠切段解决不了，只能靠 LLM

作者反复反馈「标点太少」。先后试了两条纯机械的路，**两条都失败了，第二条还让转录变慢**。

**试法一：句尾补标点。** 有效但只解决句尾——一整段仍然只有最后一个句号。

**试法二：长句切成分句，各自转录。** 假设是「Whisper 看得见句子形状才会加标点」，
所以按停顿切开就能让每片自带标点。实测推翻：

| 时长 | 是否切段 | 标点数 |
|---|---|---|
| 16.4s | 否 | **4** |
| 24.2s | **是** | **2** |

切了反而更少。再直接测单个短片段——**3.4 秒的完整中文问句**，正是切段后每片的样子：

```
无 prompt  0 个标点  「所以這個標件這問題到底應該準備解決了」
有 prompt  1 个标点  「所以这个标减的问题到底应该准备解决了。」
```

**连问号都没有。** Whisper 的中文标点在任何长度上都稀疏，切段没有任何可解锁的东西。

代价还很实在：30 秒口述被切成五六片，就是五六次模型调用，作者直接感觉到「变慢了」。

**已撤销**（`SEGMENT_ABOVE_SECONDS = None`，注释里留了完整理由和复原方法）。

**结论：判断一个中文长句里逗号该点在哪，是语言任务不是音频任务。** 它属于润色——
铁律 10 明确允许润色「补标点」，这一条从一开始就是为此写的。在接上 LLM 之前，
标点稀疏是这个方案的固有状态，不是 bug。

### 补充：同内容中英对照，以及为什么切段一定更慢

同一句话、同样长度、同一个模型，只换语言：

| | 时长 | 标点数 |
|---|---|---|
| 中文 | 10.4s | **0** |
| 英文 | 11.5s | **8** |

**标点与音频长度、与句子形状都无关，只与语言有关。** Whisper 是个序列到序列模型，
标点符号（。，）在它眼里就是普通 token，和「的」「是」一样，靠训练数据里的分布学出来。
它的中文语料大量来自字幕，字幕本身常常不带标点；英文语料多是书面转录，标点齐全。
**这个习惯长在权重里，切段不会改变它。**

而切段一定更慢，原因正是铁律 2 那条实测：

| 输入长度 | 耗时 |
|---|---|
| 3s | 1092 ms |
| 6s | 1210 ms |
| 15s | 1382 ms |
| 30s | 1367 ms |

**3 秒和 30 秒几乎同价**——Whisper 一律把 mel 补齐到 30 秒再过 encoder。
所以 30 秒切成 5 片 = 5 × 1.1s ≈ 5.5s，不切 = 1.4s，**慢四倍**。

> 这条本该一开始就想到：**铁律 2 就是从同一组数字写出来的**，它判过 v2 的死刑。
> 我却在两天后自己违反了它。规则写下来还不够，动手前得回头看一眼。

## 三方对比（2026-08-10，作者真实口述，中英混说）

素材：同一段话，中文为主，嵌 antigravity / literature review / literature matrix 等术语。

| 配置 | 中文 | 英文术语 | 标点 | 速度 |
|---|---|---|---|---|
| Whisper turbo · `zh` | 准 | **被翻译成中文** | 少 | ~1.2s |
| **Whisper turbo · 自动** | 准 | **✅ 正确** | **✅ 有** | ~2.1s |
| **SenseVoice** | **准，且有标点** | **❌ 很差** | ✅ 有 | **极快（~0.1–0.5s）** |

SenseVoice 把 antigravity 听成「安 gravity」、2.1 literature review 听成「to point one review」、
literature matrix 听成「总结这个 matrix」。**中文那一半明显优于 Whisper，英文那一半明显差于它。**

它还没有 prompt 通道，所以设计 §4.1g 第一层的术语表在它上面完全失效——**而作者的英文恰恰
几乎全是术语**，这让它的英文短板雪上加霜。

**结论：Whisper turbo + 自动检测胜出。** 那多花的 0.9 秒买到的是「两种语言都不被翻译」，
对一个中英混说的学术使用者来说是必要开销，不是浪费。

SenseVoice 留在 provider 列表里，菜单可随时切——它在纯中文场景下（快 4–12 倍、标点更好）
仍然是有价值的选项，只是不适合作默认。

## 「后面只能录到 5 秒」——排查记录（2026-08-10 深夜）

作者报告：第一句很好用，接着用后面几句「说 5 秒之后就识别不出来」，终端里
`录到音频 22.6s` 却只出来 11 个字。

### 先证伪，再修

**1. SenseVoice 不截断长音频。** 用 `say` 合成 47.1 秒中文，逐段送进去：

| 输入 | 5s | 10s | 20s | 30s | 40s | 47.1s |
|---|---|---|---|---|---|---|
| 输出字数 | 26 | 52 | 100 | 149 | 186 | 211 |
| 耗时 | 84ms | 147ms | 311ms | 765ms | — | 936ms |

线性，无平台期。同一段 47 秒连跑五次，五次都是 211 字、约 960ms——**没有状态泄漏**。

**2. 静音填充也不伤它。** 固定 10 秒语音，前后补 0–50 秒静音，输出稳定在 50–52 字。

**3. 麦克风没有衰减。** 照 daemon 的节奏开关八轮（start → 录 8s → drain → 后台
close），每轮都录到 7.9/8.0 秒，`overflows=0`、`dropped=0`。

**4. GIL 压力也不会饿死录音线程。** 并发 0/1/3/6 个满速 Python 线程，采集率
不变（98.7%），没有一次 overflow。这条否掉了「泄漏的电平线程把录音挤掉」的假设。

### 真正找到的 bug：报告和句子对不上

`_process_inner` 里 `self.last_timing = watch` 写在 `on_text(utterance)` **之后**，
而 CLI 的 `show()` 正是在 `on_text` 里打印报告。于是终端上每一块耗时数据属于
**上一句**，第一句则完全没有报告。

这不是排版问题。当晚整整一轮分析是拿「37.8 秒音频」去配「11 个字的转写」做的，
两者根本不是同一句——真实配对是 37.8s → 140 字（完全正常）。**假设找错了方向，
就是因为仪表本身在撒谎。** 现在 `watch` 一建出来就赋值，Stopwatch 是可变对象，
边跑边填。

### 补上的仪表

原来只有「录到音频 X 秒」，回答不了「那 X 秒里到底有什么」。现在：

```
录到音频 22.6s（按住 23.0s，其中说话 3.1s）
```

- **按住**：热键按下到抬起的墙钟。麦克风比按键晚约 220ms 开，所以差 1 秒以上才
  报警——那是真的没录进来，跟模型无关。
- **其中说话**：silero 全量扫一遍。代价 30 秒音频 86ms、47 秒 138ms（早退版本
  约 1ms）。**不便宜，但值**：一整晚的猜测都在猜这个数。
- **系统丢了 N 次输入缓冲**：PortAudio 的 overflow 计数从第一天就在数，从来没
  显示过——正是本项目反复承诺不做的那种静默丢失。

三条合起来，下一次复现就能一眼分清是「录音丢了」「按着没说话」还是「模型吃掉了」。

## 「有没有更大更好的 SenseVoice？」——查过了，没有（2026-08-10）

作者问：既然 SenseVoice 只有 600 多兆、而且下的是轻量档，有没有大一点、英文好一点
的版本？如果有，就只留它、把 Whisper 删掉。

三条都查了、都测了，答案都是否定的。

### 1. SenseVoice-Large 没有开放权重

[FunAudioLLM 的 HF 主页](https://huggingface.co/FunAudioLLM)只有 `SenseVoiceSmall`
（及其 GGUF）。论文里的 Large 只在阿里云 API 上，没有可下载的权重。**所谓「换个大档」
在本地这条路上不存在。**

### 2. 不是量化的锅：全精度权重一模一样，还慢一倍

同一个 repo 里躺着未量化的 `model.onnx`（938MB，我们用的 int8 是 239MB）。下下来
一测：

| | 英文 14.8s | 中英混 18.8s |
|---|---|---|
| int8 239MB | 213ms | 275ms |
| fp32 938MB | 498ms | 635ms |

输出**逐字相同的错**——`Liature review`、`Forization`、`Chriss and Van Leon`。
量化没伤到它，**是这个 234M 参数的模型本身英文就弱**。938MB 已删。

### 3. 一个更要命的发现：中文句子里的英文，它不是听错，是删掉

这条比「英文差」严重得多。测试句：

> 我这一节想写的是 literature review，大概在 2.1 的位置。然后我会做一个
> literature matrix，把 Kress 和 van Leeuwen 的 semiotic resource 放进去。

SenseVoice 交出：

> 我这一节想写的是**re盖**在2.1的位置，然后我会做一个**把ro和放进去**……

`literature review` 塌成「re盖」，`literature matrix` **整个消失**，
`Kress 和 van Leeuwen 的 semiotic resource` 只剩「把ro和放进去」。

**这是静默丢失**——中文读着通顺，英文术语没了，作者事后不会发现。对一个英文几乎
全是术语的使用者，这一条单独就足以否掉它作默认档。provider 的 `display_name`
因此改成「SenseVoice（中文快，但会吞掉英文）」：菜单必须把代价写在名字上。

### 4. 更大的开源模型试过了，更差

sherpa-onnx 1.13.4 已内建 `from_qwen3_asr` / `from_fire_red_asr_ctc` /
`from_funasr_nano` 等十几个加载器（全部 onnxruntime，不碰 torch）。挑了最对口的
一个实测：**FireRedASR2-CTC zh_en int8**（778MB，专为中英训练，且是 CTC 非自回归，
理论上该很快）。

| 引擎 | 英文术语 | 中英混说 | 纯中文 47s | 速度（每秒音频） |
|---|---|---|---|---|
| SenseVoice int8 239MB | 差 | **吞掉英文** | 好，有标点 | **14–20ms** |
| FireRedASR2-CTC 778MB | 中（全大写、无标点） | 乱码 | **无标点** | 151–174ms |
| **Whisper turbo 1.6GB 自动** | **全对** | 英文在（有拼写偏差） | 好 | 90–146ms |

Whisper 那句英文一字不差：

> Antigravity. Section 2.1. Literature Review. I will build a literature matrix.
> Foreignization and domestication are Venuti's terms in translation studies.
> The semiotic resource has a meaning potential that Kress and Van Leeuwen describe.

Venuti、Kress、Van Leeuwen 全中。FireRed 比 SenseVoice 英文好一点，但**比 Whisper
还慢，中文没标点，英文全大写**——三头不占。742MB 已删。

**结论：Whisper turbo 自动档是唯一能同时拿下两种语言的本地模型，删不得。**
SenseVoice 留作纯中文快档，代价写进名字里。
