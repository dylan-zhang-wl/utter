# P2a 听写延迟实测（2026-08-10）

机器 Apple M2 / 16G，`mlx-community/whisper-large-v3-turbo`（均衡档）。
目标：不开润色 ≤1500ms。

## 结论：达标，但有两个坑是只有真机跑才暴露的

| 按住时长 | 合计延迟 | 判定 |
|---|---|---|
| 2s | 1041 ms | ✅ |
| 4s | 968 ms | ✅ |
| 8s | 1053 ms | ✅ |

启动预热 3.3s（一次性，把 P1 记录的"第一句 2.76s"移出了用户路径）。

## 坑一：自动语言检测让延迟翻倍

8 秒音频，各测 3 次取中位：

| 设置 | 耗时 |
|---|---|
| `language="en"` | **1067 ms** |
| `language="zh"` | **1057 ms** |
| `language=None`（自动检测） | **1927 ms** |

**差额 860ms 是 Whisper 为了猜语言额外过的一遍 encoder。** 它比整个延迟预算的一半还多，
自动检测状态下无论如何撞不到 1500ms 目标。

配置项 `dictate_language` 默认仍是 `None`——作者中英双语写作，猜错语言比慢一点更糟——
但 `utter dictate` 启动时会明说这个代价。**作者确定某次是单语口述时，设一行配置省一半延迟。**

> 排查过程记一笔：最初怀疑是 pynput 的事件监听线程抢 CPU（macOS 事件 tap 跑高优先级 runloop）。
> 对照实验证否——有无监听器都是 1070ms。**不要凭直觉归咎于最可疑的组件。**

## 坑二：对着静音按热键，Whisper 会凭空编出句子

实测：房间无人说话时按住 2.5 秒，转录结果是 `"you"`，第二次是 `"Good job."`。

按住说模式的分段器是手指，不经过 VAD，所以这个洞一直开着。
**往作者文档里注入一句它自己编的话，是本项目能犯的最严重的错误**——比任何延迟问题都严重。

修法：转录前先用 silero 过一遍（`backend/vad.py: has_speech`）。代价 1–136ms，
静音时直接丢弃、模型根本不启动：

```
  hotkey → buffer closed          3 ms
  speech check                  100 ms
  transcription            (no speech)
  ────────────────────────────────────
  total                         103 ms      ← 而不是 1956ms + 一句假话
```

## 坑三：PortAudio 关流 130ms 挡在关键路径上

拆解 `end_utterance`：排空队列 0.1ms，拼接数组 0.1ms，**关闭音频流 130.6ms**。

改成先取音频入队、再异步关流后，`hotkey → buffer closed` 从 119ms 降到 **3ms**。

## 热键：右 Option 单键

按住 350ms 测得 334ms，开销约 8–16ms。左 Option 正确不触发。

pynput 有两个坑：`HotKey.parse("<alt_r>")` 产出裸键码而监听器报 `Key.alt_r`，两者永不相等；
且 `canonical()` 会把 `Key.alt_r` 折叠成 `Key.alt`。都已在 `backend/hotkey.py` 绕过。

## 剪贴板保真

五种 flavour（纯文本 / RTF / HTML / 二进制 PNG / macOS 派生的 UTF-16）写入再还原，
**逐字节一致**。铁律 12 的"粘完还原"成立。

## 坑四：中英混说时，Whisper 会把中文「翻译」成英文

作者实测（2026-08-10）：一整句英文学术论述后面接一句中文提问「这句话是什么意思呢？」，
自动检测档下输出成了 `This is what means?`——**中文被翻译了，不是转录**。

原理不是 bug 而是结构：**Whisper 每 30 秒窗口只带一个语言标签**。前段英文占主导，
检测判定为英语，解码器就被约束在英语 token 上；听到中文时它无法输出中文，
只能"用英语说出来"。第二次测试中英穿插较均匀，检测结果不同，两种语言就都保住了——
**这也说明自动检测的结果依赖哪种语言占主导，不稳定。**

固定语言实测（13 秒纯英文素材，含 Venuti 等术语）：

| 设置 | 耗时 | 纯英文结果 |
|---|---|---|
| `language="en"` | 1123 ms | 正确 |
| **`language="zh"`** | **1155 ms** | **正确** |
| `language=None` | 2031 ms | 正确 |

**`zh` 是严格最优解**：中文不被翻掉、英文术语照常保留、省掉 880ms 检测开销。
唯一代价是句号后不加空格（中文排版习惯），润色档可补。

`dictate_language` 默认值因此从 `None` 改为 `"zh"`。**这是为本作者的双语使用场景选的，
不是普适默认**——纯英语用户应设 `"en"`。

> 与 P2b 的关系：设计 §9 待决 3 原本就排了「中英混说用哪档模型」的实测。
> 这条给它加了一个具体判据——**候选模型必须在句内语码转换上不做翻译**。
> SenseVoice 宣称中英混说更强，值得优先比。

## 坑五：铁律 1 的标量 temperature 导致复读死循环

作者实测（2026-08-10）：一次 26.9 秒的口述，输出是 `of the model sign` **重复约五十遍**。

根因在 Whisper 的解码循环里：

```python
if decode_result.compression_ratio > compression_ratio_threshold:
    needs_fallback = True  # too repetitive
```

**那条 temperature 阶梯的用途，正是检测并逃出复读。** P1 为了延迟把它设成标量 `0.0`，
阶梯只剩一级——**检测照常触发，但无处可退**，于是循环跑到窗口结束。

也就是说，铁律 1 把「偶尔慢 8 秒」换成了「偶尔吐出五十遍同一句」。后者严重得多。

修正为两级 `(0.0, 0.2)`，并关掉 `condition_on_previous_text`（它把一个窗口里开始的复读
喂进下一个窗口，是循环自我强化的通道）。正常情况零额外代价：

| 音频长度 | 有界阶梯耗时 | 最高词频 |
|---|---|---|
| 3s | 951 ms | 1 |
| 8s | 1050 ms | 3 |
| 27s | 1393 ms | 6 |

第二级只在第一级产出退化时才跑，最坏情况约 2.2 秒。

## 坑六：中文标点靠切段解决不了，只能靠 LLM

作者反复反馈「标点太少」。先后试了两条纯机械的路，**两条都失败了，第二条还让转录变慢**。

**试法一：句尾补标点。** 有效但只解决句尾——一整段仍然只有最后一个句号。

**试法二：长句切成分句，各自转录。** 假设是「Whisper 看得见句子形状才会加标点」，
所以按停顿切开就能让每片自带标点。实测推翻：

| 时长 | 是否切段 | 标点数 |
|---|---|---|
| 16.4s | 否 | **4** |
| 24.2s | **是** | **2** |

切了反而更少。再直接测单个短片段——**3.4 秒的完整中文问句**，正是切段后每片的样子：

```
无 prompt  0 个标点  「所以這個標件這問題到底應該準備解決了」
有 prompt  1 个标点  「所以这个标减的问题到底应该准备解决了。」
```

**连问号都没有。** Whisper 的中文标点在任何长度上都稀疏，切段没有任何可解锁的东西。

代价还很实在：30 秒口述被切成五六片，就是五六次模型调用，作者直接感觉到「变慢了」。

**已撤销**（`SEGMENT_ABOVE_SECONDS = None`，注释里留了完整理由和复原方法）。

**结论：判断一个中文长句里逗号该点在哪，是语言任务不是音频任务。** 它属于润色——
铁律 10 明确允许润色「补标点」，这一条从一开始就是为此写的。在接上 LLM 之前，
标点稀疏是这个方案的固有状态，不是 bug。
