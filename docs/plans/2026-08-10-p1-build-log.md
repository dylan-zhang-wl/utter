## 三、被实测推翻的三条既有说法

**1. `mlx-whisper` 声明依赖 torch（476M），铁律 5 一装就破。**
实查：torch 的引用全在 `mlx_whisper/torch_whisper.py`，那是把 OpenAI 原版 PyTorch 权重转成
MLX 格式的工具，**推理路径上无人 import 它**。卸掉 torch 后转录正常，`torch` 连
`sys.modules` 都没进。已用 `requirements-overrides.txt` 把这条依赖解析掉，环境 1.1G → 613M。

> **若要推翻：** 删掉 `requirements-overrides.txt` 即可恢复安装 torch。但请先看该文件里记录的证据。

**2. 那条用来验证"无 torch"的命令本身会假通过。**
计划里写的 `~/.venvs/utter/bin/pip list | grep -i torch`——**uv 建的 venv 不装 pip**，
所以这条管道 grep 的是空输出，无论 torch 在不在都打印不出东西。它在本次执行中真的骗过了我一轮。
现已改为测试强制（`backend/tests/test_dependencies.py`）。手工查请用
`uv pip list --python ~/.venvs/utter/bin/python`。

**3. 设计 §5.3 的模型体积估值约为真实值的一半。**

| 档位 | 设计原写 | 实测 |
|---|---|---|
| 高精度 | 1.5G | **3.08G** |
| 均衡 | 0.8G | **1.61G** |

用户是看着这个数字决定要不要在计费网络下下载的，已全部改为 HuggingFace API 实测值，
设计文档同步更正。

## 四、需要你点头或知情的自主决定

按"若你不同意，代价多大"排序。

### 4.1 数据迁移改成复制，不是移动 —— 偏离了设计原文

设计 §6 写的是"整体搬迁"。实现为**复制**：`~/Utter/` 建好后 `~/LiveScribe/` 原样保留。

理由：那 3 个 v1 会话是世上唯一副本、共 3KB，移动没有任何收益，搬砸了找不回来。
旧目录留给你自己删。

**已在你的真实主目录执行。** 已核实：`~/Utter/sessions/` 有 3 个文件，`~/LiveScribe/sessions/`
原件仍在。若你希望改成移动，改 `backend/config.py: migrate_legacy`。

### 4.2 `openai_api_key` 不再出现在 `GET /config` 的响应里 —— 行为变更

v1 的 `GET /config` 返回 `config.model_dump()`，其中**包含明文 API key**——任何能访问
localhost:8765 的本地进程都读得到。新实现把该字段设为 `exclude=True`，所以它同时从
JSON 文件和 HTTP 响应里消失。

这修掉了一个 v1 的泄漏，但**如果前端某处依赖从 `GET /config` 读回 key，会静默拿到空值**。
P3 重写 `main.py` 时会彻底清掉这个字段。

### 4.3 CT2 均衡档的模型仓库已易主

`mobiuslabsgmbh/faster-whisper-large-v3-turbo`（faster-whisper 1.2.1 内置名）已转给
`dropbox-dash/faster-whisper-large-v3-turbo`。HF 靠重定向兜着，两个名字下载量都是 164 万，
所以这是 HF 记录在案的所有权转移、不是劫持。

catalog 里写的是新的规范名，理由：首次下载不该依赖重定向，且这样联网测试才能发现下一次搬家。
**但"模型仓库换主人"本身是供应链层面的事实，值得你知道。** 备选是
`deepdml/faster-whisper-large-v3-turbo-ct2`（10 万下载、218 赞）。
这条只影响非 Apple Silicon 机器。

### 4.4 VAD 权重取自 faster-whisper 自带的文件，不另行下载

faster-whisper 已随包发 `silero_vad_v6.onnx`（1.2M），而它是无条件依赖，所以零下载。
代码只是**按路径读这个数据文件**，不 import faster_whisper、不碰它的推理代码，
因此不算违反铁律 6——但这是我的判断，你可以不同意。

附带处理了一个真问题：silero 各版本 ONNX 的接口不同（v4 要 `sr`，v5 用 `state`，v6 用 `h`/`c`），
所以代码在加载时读图的输入名再决定怎么喂，而不是钉死某个版本。

### 4.5 配置里提前加入了 P2 的字段

`polish_enabled=False`、`polish_level="light"`、`vocabulary=[]` 三个字段在 P1 就落地了。
理由：**把铁律 10 写成默认值比写成文档更可靠**，而且避免 P2 再做一次配置迁移。

### 4.6 `transcribe()` 协议从第一天就带 `initial_prompt`

否则 P2 加词表时要改每一个 provider 实现。这个决定当晚就被实测证明是对的（见下）。

### 4.7 润色结果短于原文一半即拒绝采用

`safe_polish` 会在结果为空、或短于输入 50% 时退回原文。防的是模型回一句 "OK" 或
吞掉一半内容却被当作成品写进你的文档。**阈值 50% 是我拍的**，可调。

### 4.8 两个默认模型名是猜的，未经验证

`OllamaProvider` 默认 `qwen3:4b`，`OpenAICompatProvider` 默认 `gpt-4o-mini`。
本机两者都跑不起来（见下），所以**这两个名字一次都没被真正调用过**。P2a 接通时请复核。

## 五、当晚最有价值的一条实测

基准素材里，**"foreignisation" 被 Whisper 听成了 "Thorinization"**——翻译研究的核心术语，
听成了托尔金。把术语表作为 `initial_prompt` 喂进去后：

| | 耗时 | 输出 |
|---|---|---|
| 不带词表 | 1.15s | **Thorinization**, by contrast… |
| 带词表 | 1.14s | **foreignisation**, by contrast… |

**零延迟代价修好。** 这把设计 §4.1g 第 1 层从主张变成了结论，而且说明了为什么它必须在
转录时做而不是交给下游 LLM——"Thorinization" 和 "foreignisation" 字面相去太远，
下游模型没有任何线索能猜回去。

**推论：术语表应该是 P2a 的一等功能，不是可选项。** 你写的是翻译研究，
满篇都是这类会被听错的专名。
