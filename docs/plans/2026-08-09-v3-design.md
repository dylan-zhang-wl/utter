# Utter v3 设计：本地优先的可分发双模语音平台

**日期：** 2026-08-09
**项目更名：** LiveScribe → **Utter**（2026-08-09 定）。v1/v2 文档中的 "LiveScribe" 均指本项目旧名。
**取代：** `2026-04-14-livescribe-v2-design.md` 与 `2026-04-14-livescribe-v2-implementation.md`
**语言说明：** 本文是决策文档，用中文；后续的 TDD 实现计划仍按 v1/v2 惯例用英文写（那是给 Claude 执行的规格）。

## 1. 为什么改版

v2 冻结于 2026-04-15，此后四个月项目休眠。三件新事实使 v2 的设计前提失效：

1. **本机已有 `mlx-community/whisper-large-v3-turbo`（1.5G，MLX 格式）**，2026-08-01 因 digital-human 项目下载。它跑 Apple Silicon GPU，精度与速度都远超 v1 用的 faster-whisper `small`（CPU / int8）。v2 设计文档自列的痛点之三"非母语者准确率一般"，其原方案是 base→small，属杯水车薪；换 large-v3-turbo 才是对症。
2. **实测推翻了 v2 的 partial 管线**（见 §3）。v2 的核心管线设计不可用。
3. **目标从"我一台 M2 上的听课工具"扩展为"可分发的双模平台"**：既做实时听（讲座/会议转录+翻译），也做说（听写注入光标）；模型层可插拔；能给自己的其他设备和同学使用，由他们自选 STT 模型与 LLM。

第 3 条是根本性的——v2 通篇假设单模式、单 provider、单机器，这个假设整个不成立了。

## 2. 目标与非目标

**目标**

- 一套底座、两种模式，模式之间共享音频、模型、配置、历史。
- **本地优先**：默认全链路离线（本地 STT + 本地 LLM），未刊稿与保密译稿不出机器。
- **可插拔**：STT 与 LLM 都是 provider 接口，用户自选下载哪个模型、接哪个 LLM。
- **可分发**：能打包给非本机、非本人使用，含首次运行向导与模型下载器。

**非目标（本轮）**

- 移动端。
- 说话人分离（diarization）。
- 多语言源——听的方向仍只做 EN→ZH；说的方向支持中英混说。
- 云同步、账号体系。

## 3. 实测基准（2026-08-09，M2 / 16G，60s 英语讲话素材）

用本机已有的 large-v3-turbo 实测，`mlx_whisper 0.4.3`。脚本见 `docs/benchmarks/2026-08-09-mlx-whisper-latency.py`，下表取两次独立运行的区间：

| 块长 | 单次耗时 | 实时倍率 |
|---|---|---|
| 2s | 0.94–1.00s | 约 2x |
| 5s | 1.00–1.01s | 约 5x |
| 8s | 1.03–1.04s | 约 8x |
| 15s | 1.11–1.20s | 约 13x |
| 30s | 2.21–2.35s | 约 13x |

**三个结论，都直接决定架构：**

**(a) 短块不便宜。** 2s 与 15s 耗时几乎相同（约 1s），因为 Whisper 内部一律把 mel 补到 30 秒过 encoder。**推论：任何"高频小增量刷新"的设计都是错的。**

**(b) v2 的 partial 策略作废。** v2 设计要求"每 1s 对累积中的整句重转一次"。实测模拟一句 8 秒的话，累计 GPU 占用 13.8s / 17.7s（两次运行）对 8s 说话时间 = **占空比 172% / 221%**，永久性掉队。此设计必须删除。

**(c) 定稿式管线完全够用。** VAD 分句 + 每句只转一次：每句话说完约 **1.1 秒**出字，占空比约 20–25%，余量足够跑翻译。对比 v1 的 8 秒缓冲 + 约 10 秒滞后，这是能否跟住讲者的分界线。

**附带修复（必须写进实现）：** 默认参数下部分块会跳到 6–8 秒。查明是 Whisper 的 temperature fallback 阶梯（0.0→1.0 六档重试）。实测：

| 设置 | 3s 块耗时（两次运行） |
|---|---|
| 默认（带 fallback） | 8.19s / 10.84s |
| `temperature=0.0` | 0.96s / 0.98s |

实时管线必须固定 `temperature=0.0`，把最坏情况从 8–11s 压到约 1.0s。代价是放弃 fallback 的纠错，但实时场景下"慢 8 秒"比"偶尔差一句"严重得多。

## 4. 架构：五槽管线，模式即预设

两种模式的管线**形状相同**，只是每个槽绑不同实现。这是"融合"能成立而非硬拼的根据：

```
AudioSource → Segmenter → SttProvider → PostProcessor → Sink
```

| 槽 | 听（LiveScribe 模式） | 说（Dictation 模式） |
|---|---|---|
| AudioSource | 麦克风 \| 系统音频（BlackHole） | 麦克风 |
| Segmenter | VAD：600ms 静音定稿，30s 硬上限 | **按键边界**：热键按下→抬起即一段 |
| SttProvider | 同一个（用户选） | 同一个（用户选） |
| PostProcessor | 翻译 EN→ZH | 润色：去口水词、加标点、套个人术语表 |
| Sink | 字幕面板 + 会话文件 | 光标处注入 |

注意 Dictation 模式**不需要 VAD**——热键本身就是分段器。这比 VAD 更可靠，也让听写模式成为验证整条链路最省的路径（见 §8 排序理由）。

## 5. Provider 抽象

### 5.1 STT

```python
class SttProvider(Protocol):
    id: str
    display_name: str
    def is_available(self) -> tuple[bool, str]:   # 平台/依赖检测，失败给可读原因
    def transcribe(self, audio: np.ndarray, language: str | None) -> str: ...
```

| 实现 | 适用 | 说明 |
|---|---|---|
| `MlxWhisperProvider` | **Apple Silicon 专属** | 本机首选。GPU 推理，固定 `temperature=0.0` |
| `FasterWhisperProvider` | 跨平台 CPU / CUDA | Intel Mac、Windows、无 GPU 机器的回退。v1 已有代码可复用 |
| `CloudSttProvider` | 任意平台，BYOK | Groq（跑 large-v3-turbo，极低延迟）/ Deepgram。弱机器或极限延迟场景 |

> **注意区分「模型」与「运行格式」。** Whisper 本身跨平台，受限的是格式：MLX 仅 Apple Silicon（Metal GPU）；CTranslate2 覆盖各平台 CPU 与 NVIDIA CUDA；GGUF（whisper.cpp）几乎无所不跑，含老 Intel 机。**同一档模型在不同机器上下载不同格式即可。** provider 抽象的作用就是把这层差异藏起来——用户只选档位，格式由平台按硬件自动挑。
>
> **用户已确认持有非 Apple Silicon 设备**，故 `FasterWhisperProvider`（或 whisper.cpp 绑定）不是"以后再补"，**在 P1 就要与 MLX 一起进接口**，至少保证 catalog 与探测逻辑从第一天就是多后端的。

### 5.2 LLM（供翻译与润色共用）

> **BYOK = Bring Your Own Key（自带密钥）**：软件本身不含任何 API key，由使用者自己注册并填入。意义在于分发时你不替任何人付费、也不承担 key 泄漏风险。下文凡出现 BYOK 均指此。

| 实现 | 说明 |
|---|---|
| `OllamaProvider` | 本地，默认。全离线的那一半靠它 |
| `OpenAICompatProvider` | BYOK，一套接口覆盖 OpenAI / DeepSeek / Groq / 硅基流动等 |
| `FreeTranslateProvider` | deep-translator，仅翻译、无需 key，**仅作兜底** |

> v1 的教训要写进文档：deep-translator 的免费 Google 端点无 SLA，一节 90 分钟讲座数百次调用会被限流，v1 届时只静默写入 `[translation error]`。免费通道只能是兜底，不能是默认。

### 5.3 模型管理：用户只选档位，格式由平台决定

**用户看到的（不出现任何格式术语）：**

| 档位 | 说明 | 体积 |
|---|---|---|
| 高精度 | 最准，口音与专业术语都稳；需要较新的机器 | 约 1.5G |
| **均衡（推荐）** | 准确度接近高精度，但快得多。日常首选 | 约 0.8G |
| 轻量 | 一般机器也流畅，长词与术语偶尔出错 | 约 0.5G |
| 极轻 | 老机器或内存紧张时应急，准确度明显下降 | 约 0.15G |

> **一个要避免的误导：** 直觉上"权重大＝慢"，但 `large-v3-turbo` 是例外——它有 809M 参数却只有 4 层 decoder（large-v3 是 32 层），所以**又大又快**。这正是"均衡"档推荐它的原因，也是本机实测 1 秒出字的来源。档位文案不要写成"大＝慢、小＝快"的线性梯度。

**平台内部的映射（用户不可见）：** 首次运行探测硬件（Apple Silicon？NVIDIA GPU？仅 CPU？内存多少），再决定同一档下载哪种格式。

| 档位 | Apple Silicon | NVIDIA GPU | 仅 CPU |
|---|---|---|---|
| 高精度 | `whisper-large-v3-mlx` | faster-whisper `large-v3` (CUDA) | whisper.cpp `large-v3` 量化 |
| 均衡 | `whisper-large-v3-turbo` | faster-whisper `large-v3-turbo` | whisper.cpp `turbo` 量化 |
| 轻量 | `whisper-medium-mlx-4bit` | faster-whisper `small` | whisper.cpp `small` 量化 |
| 极轻 | `whisper-base-mlx-q4` | faster-whisper `base` | whisper.cpp `base` 量化 |

**非 Whisper 的候选**（catalog 应留位，不必首发全实现）：

- **Parakeet**（NVIDIA）——英语专精、极快，有 MLX 移植。纯英语听写场景可能优于 Whisper
- **SenseVoice / FunASR**（阿里）——中文显著强，**中英混说听写值得单列一档**
- **Moonshine**——极小、为端上流式设计，英语

模型管理器需要：档位目录、硬件探测、带进度的后台下载、磁盘占用显示、删除。**模型不能打进安装包**，一律首次运行时按需下载。

### 5.4 VAD：去掉 torch

v2 声明了 `silero-vad` pip 包，它拖入 **328M 的 torch**，而 v1 实际从未 import（评估已坐实为"纯陪葬"）。

v3 改用 **silero-vad 的 ONNX 权重 + onnxruntime**（约 2M）。这条路在本项目已被验证——v1 的 `faster-whisper` `vad_filter=True` 走的就是 onnxruntime。**净省 400M 依赖。**

## 6. 分发层（v2 完全没有的一整层）

**分发路线已定：GitHub 开源。** 不买 Apple Developer ID，$99 的公证留到"将来想做成正经 App"时再说。这条路是 OpenTypeless 一类项目的常规做法，成本为零：

- 同学**从源码构建** → 完全没有签名问题
- 你在 GitHub 发**预编译包** → 对方首次打开会被 Gatekeeper 拦，右键→打开、或一行 `xattr -d com.apple.quarantine` 即可，README 写清楚即可。开源界这是常态

| 事项 | 状态与决策点 |
|---|---|
| **sidecar 打通** | 当前必须手开两个终端（`build.sh` 的 PyInstaller 产物从未构建、`sidecar.ts` 是死代码、`externalBin` 已被移除）。评估判断这很可能就是 v1 从未被用起来的机械原因。**分发的前置条件，不可省** |
| **首次运行向导** | 麦克风权限 → 辅助功能权限（光标注入必需）→ 选并下载 STT 模型 → 选 LLM（本地 Ollama / 填 key）→ 可选 BlackHole 引导 |
| **密钥存储** | BYOK 一律进 macOS Keychain，不落明文 JSON。包内不得含任何 key |
| **配置持久化** | v1 的 `PATCH /config` 只改内存、重启即失，Settings 页的 Save 是假象。v3 必须落盘 `~/Utter/config.json`（chmod 600） |
| **数据目录迁移** | `~/LiveScribe/` → `~/Utter/`。首次启动时若检测到旧目录，整体搬迁并保留（现存 3 个 v1 会话，v2 起 JSON 兼容，仅需补 `id` 字段） |
| **脚手架残留** | `productName: "frontend"`、`identifier: "com.d.frontend"`、`csp: null`、模板 `greet` 命令——identifier 会烧进 .app 身份，分发后再改等于换应用，**打包前必须清** |

## 7. v2 计划的存废清单

| v2 内容 | v3 处置 |
|---|---|
| VAD 事件驱动管线 | **保留骨架**，但去掉 partial 分支 |
| `transcribe_partial(beam=1)` / `transcribe(beam=5)` 双档 | **删除**。①实测证明高频 partial 不可行 ②`beam_size` 是 faster-whisper 惯用法，不适用于 mlx 路径 |

| 可编辑条目（英文与译文双可编辑） | **保留**，设计完好 |

| 错误处理表（VAD 假阴性 30s 硬上限、翻译失败重试、WS 断连恢复） | **保留**，是好设计 |

## 9. 已决与待决

**已决（2026-08-09 用户确认）**

1. **平台定位**：融合式双模，不是两个工具。
2. **多后端从 P1 起**：用户持有非 Apple Silicon 设备，故 catalog 与硬件探测第一天就要多后端。
3. **分发走 GitHub 开源**，不买 Developer ID。
4. **先做听写模式**——用户当前"一直在打字"，这是即时痛点。
5. **暂不建远端仓库**（用户明示）。风险自担项：3080 行设计文档 + 本文目前仅本机一份。

6. **项目更名为 Utter。** 取语言学的 *utterance*（话语）——正是 §4 里两个模式共同的处理单元：听模式由 VAD 分句得到，说模式由热键分段得到。名字与领域模型同词。英文里 "utter" 作动词即"说出"。
   - 重名核查（2026-08-09 实查 GitHub）：`utterance/utterances` 9696★ 是网页评论组件，**领域无关**。落选的 Verba 撞 `weaviate/Verba` 7712★——同属 AI 工具领域，不可接受；Parole 撞 Xfce 媒体播放器且英文有"假释"歧义。

**待决**

1. **目录改名。** `live voice transform` → `utter`。含两个空格，一切 shell 引用都要加引号。git 仓库自足，改名无副作用，但会影响本会话工作目录与既有路径引用，**需用户点头后执行**。
2. **应用标识符**：`com.d.frontend` → `com.dylan.utter`；`productName: "frontend"` → `"Utter"`。打包前必须改，identifier 会烧进 .app 身份。
3. **中英混说听写用哪档模型**——Whisper large-v3-turbo 与 SenseVoice 需实测比一次，排在 P2。
