# P3 实现计划：听模式（会议听记）

> 2026-08-16 定。上位文档是 [v3 设计](2026-08-09-v3-design.md)；本文只写听模式，
> 并**修正 v3 §4 与 §8 里已被实测推翻的两处**（见 §6）。

## 0. 做出来是什么样

一句话：**开会时打开「听记」，说的话变成中英对照的条目滚出来，会后一键出纪要。**

第一步只做**线下会议**：

```
主窗口「听记」页 → 选麦克风 → 开始
   ↓  讲者说话
条目一条条出现：英文原文 / 中文译文（都可编辑）
   ↓  结束
生成纪要（分段总结再合并）→ 导出 markdown
```

线上会议（系统音频）是**第二步**，因为音源是可替换的槽，管线不用改。

## 1. 现成的，不重做

四天真实使用（270 次口述）已经把这些验过了：

| 现成件 | 听模式怎么用 |
|---|---|
| VAD 分段（ONNX，无 torch） | 直接用。600ms 静音定稿、30s 硬上限 |
| `SttProvider` + Whisper turbo | 直接用。**长音频实测每秒音频约 100ms**，30 秒窗口约 3 秒转完 |
| `LlmProvider` | 翻译与总结共用这一层 |
| 配置、钥匙串、JSONL 存档 | 直接用 |
| `Stopwatch` 分段计时 | 直接用，听模式一样要埋点 |
| `AudioSource` 抽象 | 麦克风现成；系统音频作为**第二个实现**接进来 |

**能跟住讲者吗？** 能。一句 10 秒的话约 1 秒转完，占空比约 10%，余量足够跑翻译。
这正是 v3 §3 当初的结论，现在有四天真实数据支持。

## 2. 要新建的

### 2.1 `ListenSession` — 会话模型

照 [v2 设计](2026-04-14-livescribe-v2-implementation.md)保留的那六成写：
Start / Pause / Resume / Stop、自动保存、重命名、历史列表。

一条条目：

```python
@dataclass
class Entry:
    index: int
    started_at: float        # 相对会话开始的秒数
    source_text: str         # 转录原文
    translated: str | None   # 译文，可能还没到
    source_edited: bool      # 用户改过原文
    translated_edited: bool
```

**原文与译文分开存，永不互相覆盖。** 见 §3.1。

#### 落盘：两份记录，暂停也写

作者 2026-08-16 要求：**结束或暂停之后，记录都必须已经在盘上**，
而且要两份——一份一字不少的原文，一份中英对照的清理版。

```
~/Utter/listen/20260816-1930/
    entries.jsonl   ← 每出一条立刻追加。崩溃、断电、忘记按结束，都不丢
    原文.md         ← 一字不少的英文，未清理、未润色
    对照.md         ← 中英对照，清理过口水词
    纪要.md         ← 会后生成（任务 5）
    audio.wav       ← 会话期间存，结束即删（§3.2）
```

- `entries.jsonl` **逐条追加**，不等结束——这与听写存档同一个做法，
  为的是"忘记按停止"和"应用崩了"这两种最常见的情况
- 两份 `.md` 在**暂停**与**结束**时各重写一次；它们是从 jsonl 生成的，
  所以任何时候都能从 jsonl 重建，**jsonl 才是真身**
- **原文.md 不做任何清理**：画面上不显示口水词是显示层的事，
  存档层一个字不动

### 2.2 翻译槽：**允许联系上下文补全，但不许编造**

复用听写的**批处理 + 串行队列**（v3 §4.1a / §4.1b），不是每句一个请求：

- 一句一个请求 = 90 分钟会议约 400 次调用，撞限流也烧钱
- 攒够 3 句或停顿 >1.2s 或距上次 >8s 就发一批
- **串行**：同时只允许一个请求在飞，否则返回乱序会打乱条目顺序

翻译失败 → 条目保留原文，标记「未翻译」，**绝不丢原文**。

#### 为什么这里可以"猜"，而听写里不可以

作者的要求：转录难免丢几个词，希望大模型**联系上下文译出完整、
必要时带解释的中文**，而不是把一句残缺的英文照残缺地译过去。

**这个要求成立，而且与铁律 10 不矛盾**——差别在于**改动看不看得见**：

| | 听写润色 | 听记翻译 |
|---|---|---|
| 结果去哪 | **替换**掉原话，进你的文档 | **并排**放在原文旁边 |
| 改错了 | 事后几乎发现不了 | 抬眼就能对照英文 |
| 所以 | 一个字都不许改（铁律 10） | **可以解释性翻译** |

**但有一条硬边界，来自听写那边的教训**：那次转录出乱码「我元册圆」，
模型改成了像模像样的「语言核语言」。**编得像样的东西比明显的乱码更危险。**

所以翻译的提示词要求：**听不清就说听不清，不要编一个通顺的句子填上。**
无法复原的地方输出「……」并标记，而不是猜一个像样的说法。

#### 三档，形状与润色档位一致

| 档 | 做什么 |
|---|---|
| 直译 | 忠实译出，残缺处保持残缺 |
| **通顺**（默认） | 联系前后文补全断词、理顺语序 |
| 解释性 | 再加一句必要的背景（术语、人名、引用出处） |

上下文取**前 2–3 条**（原文+译文），与润色只带前一段是同一个做法：
请求大小与会议总长无关。**术语表在这里第二次生效**——
`foreignisation` 该译成「异化」而不是音译。

#### 拿不准的地方要标出来（需要小改 provider）

Whisper 每段其实会返回置信度，**我们现在直接丢掉了**——
`SttProvider.transcribe()` 的返回类型是 `str`。2026-08-16 实测确认返回里有：

```
per-segment: avg_logprob, no_speech_prob, compression_ratio
2 秒轻噪音 → 文本 " You"，avg_logprob=-0.82，no_speech_prob=8e-11
```

注意 **`no_speech_prob` 抓不住幻觉**（模型对这段"是人声"极有信心），
**`avg_logprob` 才是可用的信号**。

做法：给协议加一个**可选**的详细接口（`transcribe_detailed()`），
不动现有 `transcribe()`，听写一行不改。低于阈值的条目在界面上标一个淡色记号，
意思是"这句机器自己也没把握，译文更靠猜，建议核对英文"。

### 2.3 「听记」界面（AppKit）—— 尽量少的东西

**原则：窗口就是记录本身。** 除了记录，屏幕上不该有别的东西在抢注意力。
上一版画的那个（顶部一排标签、底部一条状态栏、旁边一个占用计数）
东西太多，作者要求砍掉。

```
┌────────────────────────────────────────────┐
│ [麦克风 ▾]      ● 12:34      ■ 结束    ⋯  │  ← 工具栏，就这些
├────────────────────────────────────────────┤
│                                            │
│  So the question of equivalence is not     │
│  那么对等这个问题，并不是……                  │
│                                            │
│  Venuti argues that fluency is itself      │
│  韦努蒂主张，通顺本身就是一种……               │
│                                            │
│                                            │
│                 （整扇窗都是记录）            │
│                                            │
└────────────────────────────────────────────┘
```

- **工具栏只留四样**：音源、录制中的计时、结束、一个 `⋯` 菜单
- **`⋯` 里放低频的**：保持在最前面、导出、录音占用、清空
- **没有底栏**、没有分组框、没有说明文字
- **时间戳默认不显示**（放进 `⋯` 开关）——一场会几百条，
  每条前面挂一个 `00:12` 只是噪音
- 「听记 / 设置」的切换放进工具栏，或者干脆让设置留在原窗口、
  听记单开一扇——**以少为准**

#### 口水词不写进画面

作者要求"很多的那种废话不要写上去"。会议英语里 `um / uh / you know /
I mean / sort of` 极多，逐字显示会把画面塞满。

**做法与听写一致：画面上显示清理过的，存档里保留原样。**
复用现成的 `strip_fillers()`，中文那行由大模型译出，本来就不会带口水词。
**原始转录一个字不少地进存档**——这是铁律 10 的同一条精神：
可以不显示，不可以丢失。

#### 实现要点（容易漏的两个）

**条目文本必须可选中。** `NSTableView` 的单元格默认不可选中文本，
点一下只选中整行。要在单元格里放 `setSelectable_(True)` 的 `NSTextField`，
否则"能复制"这条就是空话。

**点击、选中、滚动都不碰音频线程**，所以怎么操作都不会打断录制——
与听写现在的结构相同，录音与界面各跑各的。

#### 其余行为

| 问 | 答 |
|---|---|
| 是小浮窗吗 | 不是，是普通 macOS 窗口，能拖能缩放能上第二屏 |
| 不在最前面还录吗 | 录。四天 286 次听写全部是在别的应用最前面时完成的 |
| 窗口关掉呢 | 继续录，菜单栏显示录制中，再打开内容都在 |
| 录着能复制吗 | 能，不影响录制 |

**不用 Tauri**：sidecar 至今没修通，而 v3 §8 自己写着那很可能就是 v1
从没被真正用起来的机械原因。现有 1370 行 AppKit 界面代码已证明这条路走得通。

### 2.4 纪要生成（会后一次性）

90 分钟会议塞不进一个 prompt，走 **map-reduce**：

1. **map**：按时间或条目数切块（约 15 分钟一块），每块出要点
2. **reduce**：把各块要点合成一份纪要（议题 / 结论 / 待办）

**纪要是新写的文本，不受铁律 10 约束**——它本来就是概括。但：

- 纪要必须**标注它依据的条目区间**，能点回原文
- **原始转录与译文永远与纪要一起存档**，纪要不覆盖任何东西

## 3. 铁律在听模式下的适用

### 3.1 铁律 10 对翻译**不适用**，但要有等价保障

铁律 10 说"不得改写措辞、不得增删内容"。**翻译的本质就是改写**，
所以这条不能直接套。等价的保障是：

> **原文必须与译文一起存档，且原文永不被译文覆盖。**

用户随时能看到讲者到底说了什么。这与听写里"原始转录与润色版一起存档"是同一条原则的两种落法。

### 3.2 铁律 3（音频永不落盘）在会议场景有真实张力 —— **已定：会话期间存、结束即删**

听写时不存音频没问题：转录错了，再说一遍就是。
**但一场 90 分钟的讲座错了一句，音频没了就永远回不去了。**

| 选项 | 代价 |
|---|---|
| 坚持不落盘 | 转录错误不可回溯。符合现有铁律 |
| 会话期间存，结束即删 | 会中可回放核对，会后不留痕。折中 |
| 存下来由用户自己删 | 最有用，但**违反铁律 3**，且录音文件涉及他人隐私（会议里有别人的声音） |

**2026-08-16 用户拍板：取中间那条——会话期间存、结束即删。**
理由是他自己给的：录音既占空间，又涉及会议里其他人的隐私；
但会中能回放核对，值得留那一会儿。

**这构成铁律 3 的第一个明确例外，必须写清边界**：只有听记会话期间、
只在会话目录里、会话结束（正常结束或崩溃后下次启动）一律删除。
听写模式不受影响，仍然永不落盘。

### 3.3 铁律 2（不做高频小增量重转）继续有效

VAD 定稿一次转一次，不做"每秒刷新"。这是 v3 §3 实测证伪过的。

## 4. 明确不做

- **说话人分离**（谁在说话）。v3 §2 列为非目标；Meetily 把它放进付费版，
  说明它不便宜。继续不做。
- **混录麦克风 + 系统音频**。回声、时钟漂移、静音检测三个真问题，
  **一次只收一路**就都不存在。
- **接 Zoom / Teams 的 API 或放机器人进会议**。Hyprnote 与 Meetily 都走
  "直接抓电脑的声音"，所以什么平台都能用、也不用要权限。照抄这个选择。
- **中英混说的会议**。Whisper 每 30 秒窗口只认一种语言，英文讲座里插一段中文提问
  会翻车。这是设计限制，**在界面上说清楚，不假装能处理**。

所以放最后，卡住了也不影响前面能用。

## 6. 对 v3 设计的两处修正

### 6.1 「系统音频走 BlackHole」——作废

v3 §4 与 §6 写着系统音频要用 BlackHole 虚拟声卡，并把"BlackHole 引导"
列进首次运行向导。**这条基于 2026-04 的认知，现在过时了。**

macOS 14.4 起有 **Core Audio Taps**（`AudioHardwareCreateProcessTap`），
只要"系统录音"权限，**不用装任何驱动**。2026-08-16 在本机实测：

```
macOS 26.6.1，pyobjc-framework-coreaudio 12.2.1（本来就装了）
CATapDescription available: True
AudioHardwareCreateProcessTap -> err=0 tapID=180
✓ 纯 Python 建成系统音频抓取通道，零新依赖
```

**还没验的**：从 tap 建聚合设备并读出采样。已知坑（来自 Apple 文档与社区）：
`AVAudioEngine` 不能被重定向到 tap 支撑的聚合设备——设了
`kAudioOutputUnitProperty_CurrentDevice` 会返回 `noErr` 却仍在读默认输入，
要直接用 `AudioDeviceCreateIOProcIDWithBlock`。
**若聚合设备能出现在系统设备列表里，`sounddevice` 直接按 index 读即可，
现有 `AudioSource` 一行不用改。这是任务 7 要先验的第一件事。**

**不用 ScreenCaptureKit**：它要"屏幕录制"权限（比"系统录音"吓人得多），
而且录到的声音不隔离——通知声、音乐会混进去。

### 6.2 听模式新增「总结」

v3 §4 的听模式出口只写了"字幕面板 + 会话文件"，没有纪要。
2026-08-16 用户要求加上，见 §2.4。

## 7. 可行性复核（2026-08-16，用户追问后逐条查证）

### 7.1 模型：同类都用 Whisper 吗？我们该用哪个

不全是。当前两强是 Whisper 与 **NVIDIA Parakeet**（Meetily 两个都带）。
[Open ASR 榜](https://openwhispr.com/blog/parakeet-vs-whisper-vs-nemotron)上
Parakeet TDT 0.6B v3 英文平均 **WER 6.32%**，Whisper large-v3 **7.44%**，
且 Parakeet 快约 4 倍。

**但我们仍然用 Whisper，有三条具体理由：**

| | Parakeet | Whisper |
|---|---|---|
| 干净英文 | **更准更快** | 稍逊 |
| **口音重** | 明显变差 | **更稳** |
| **远场／混响**（会议室） | 明显变差 | **更稳** |
| **中文** | **完全不支持**（v3 只覆盖 25 种欧洲语言） | 支持 |

作者在英国开的会：国际口音、会议室远场、可能夹中文提问——**三项全踩在
Parakeet 的弱项上**。榜单第一名不等于我们的场景第一名。

Parakeet 值得日后作为「纯英文快档」提供，形状与 SenseVoice 那档完全一样
（更快、有明确代价、名字里写清楚）。**不进第一步。**

### 7.2 噪音与环境：怎么区分人声

**结论：不需要我们自己做降噪。** 已有三层，前两层项目里已经有了：

1. **VAD（silero，已有）** —— 判断"这段是不是人在说话"。
   翻页、挪椅子、空调声不会被送进转录。这是最重要的一层。
2. **Whisper 自身的抗噪** —— 它在 68 万小时嘈杂网络音频上训练，
   对背景噪音本来就比传统 ASR 稳。
3. **系统层（可选，不默认开）** —— macOS 有 Voice Isolation（控制中心里
   用户自己开）和 `AUVoiceProcessingIO`（回声消除+降噪+自动增益）。

**但第 3 层我建议默认不开。** `AUVoiceProcessingIO`
[会同时压低麦克风和扬声器的增益](https://developer.apple.com/forums/thread/733733)，
且要求输入输出都进 voice processing 模式——它是为双向通话设计的，
**会改变你在会议里听到的声音**。为了转录去动用户的会议音频，代价不对。

**真正的限制不是算法，是麦克风离讲者多远。** 会议室里笔记本麦克风隔三米
录到的是混响，没有软件能补回来。这一条要在界面上说实话。

**线上会议因此会明显比线下准**——系统音频是干净的数字流，没有房间、
没有混响、没有环境噪音。这是把系统音频排进第二步的另一个理由。

#### 三层防线各挡什么（2026-08-16 实测）

|  | VAD 放行 | 绕过 VAD 时的置信度 | 转出来的文本 |
|---|---|---|---|
| 纯静音 30s | **0 段** | -0.242 | `Thank you.` |
| 轻噪音 30s | **0 段** | -0.819 | `You` |
| 空调声 30s | **0 段** | — | — |
| 真实语音 18.6s | 1 段 / 18.4s | **-0.101** | 正确 |

**结论一：干活的是 VAD。** 静音和噪音**根本到不了 Whisper**，所以那些著名的
静音幻觉在本项目的结构里基本不会发生——上面那两条是我直接调 provider、
绕过 VAD 才逼出来的。

**结论二：置信度不是幻觉过滤器。** 它能把真实语音（-0.101）和噪音里编的字
（-0.819）分开，**但静音里编的 `Thank you.` 是 -0.242**，和真实语音离得太近，
任何"保住真话"的阈值都拦不住它。所以置信度只能用来提示
"这句要不要核对一下"，不能拿来删东西。

**结论三：不要因此去扩充幻觉短语表。** `Thank you.` 没被短语表拦下，
但**加进去就会误杀会议里真的有人只说一句「谢谢」**。为一个 VAD 已经挡住的
风险去冒误删真话的险，划不来。**先量，再决定要不要修。**

**会议场景真正的 Whisper 风险是「静音里编字」**：会议有大量长静音
（换人、翻页、沉默），而 Whisper
[在静音与非语音段会凭空生成句子](https://arxiv.org/pdf/2501.11378)。
现有三道防线继续有效：VAD 先拦、幻觉短语表、复读折叠
（四天实测触发过 1 次）。**会议比口述暴露得多，要重点盯。**

### 7.3 后台运行：切到 Word 也继续转录

**能，而且已经有 286 次实证。** 四天里每一次听写热键按下时，
最前面的窗口都是 ChatGPT / Antigravity / Claude / 微信——
**Utter 一次都不在最前面**，录音与转录全部正常。macOS 不像 iOS，
不会因为应用不在前台就掐掉音频输入。

两件要额外做的：

**(a) 挡住 App Nap。** macOS 会给"不在前台、没在播声音、用户没在操作"的
进程降频。听记会话期间取一个活动断言即可：

```python
NSProcessInfo.processInfo().beginActivityWithOptions_reason_(
    NSActivityUserInitiated, "Utter 听记会话")
```

**(b) 别让机器睡着，但要让屏幕能黑。** 2026-08-16 实测（正是作者早先
要求过的那个组合）：

```
PreventUserIdleSystemSleep     1   ← 机器不睡，转录继续
PreventUserIdleDisplaySleep    0   ← 屏幕照常熄灭
```

`NSActivityUserInitiated` 含 `IdleSystemSleepDisabled`、
**不含** `IdleDisplaySleepDisabled`，正好是要的语义。
会话结束必须 `endActivity_` 释放——否则就变成本项目 08-12 那天
替用户杀掉的那个 `caffeinate -d`。

**(c) 长时会话的内存**：90 分钟音频若全留在内存是 345MB。不会——
VAD 切一段转一段即弃，内存里最多一段（≤30s，约 2MB）。
但 §3.2 那份"会话期间存盘"的录音，90 分钟 16kHz 单声道约 170MB，
**结束即删**，要在界面上显示当前占用。

### 7.4 麦克风冲突：作者的方案可行，且理由比"技术冲突"更硬

作者提议：线下听记开着时，口述暂时不可用，按热键给明确提示。**这个方案对，采纳。**

需要补一层理由——**macOS 其实允许多个流同时读同一个麦克风**，
所以这不是技术上的硬冲突。真正的原因是**内容**：

> 线下会议时房间麦克风**也听得见你**。你口述的每一句话，
> 本来就会进到会议记录里。所以"开会时口述一条私人笔记"这件事，
> 在线下场景**物理上不可能**，不是我们不给做。

因此做法是：听记（麦克风源）进行中按热键 → 浮窗明确显示
**「麦克风正在用于听记」**，不静默失败。这与铁律 13 同一条原则：
明确失败远好过随机失败。

**线上会议不冲突**：听记走系统音频、口述走麦克风，两件事各走各的，
可以同时用。这也正是作者要的"听说同时存在"。
